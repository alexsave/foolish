T2a — Helgrind race-freedom gate (digest; raw valgrind logs not committed)

Tool: valgrind --tool=helgrind --history-level=approx
Technique: launch valgrind directly on foolish_server (never through `timeout`
— it forks an untraced child, so a callgrind/helgrind capture measures only
`timeout`'s own startup; see PROFILE_HOTPATH.md's note on the same issue),
drive it with foolish_hammer for a bounded window, then `kill -TERM` the
valgrind PID so it forwards the signal, the guest's blocking accept()/read()
unwinds, and valgrind flushes its report before exiting.

=== Run 1 (first per-game-lock-only build, BEFORE g_kernel_lock existed) ===
cmd: valgrind --tool=helgrind -- ./foolish_server 8098
load: foolish_hammer --mode=mixed (games=3 seats=4 conns=6 secs=15)
      then foolish_hammer --mode=ws (games=3 seats=2 secs=15)
RESULT: Possible data race during write of size 4 on `engine_last_reject`
  (game.c) between two DIFFERENT games' threads, each correctly holding its
  own GameSlot.lock — see SERVER_SCALING.md "What Helgrind found" for the
  full analysis and the kernel-source citation explaining why. NOT
  Helgrind-clean.
FIX: g_kernel_lock added around awire_apply / bot_drive / game_seat_and_deal.

=== Run 2 (after g_kernel_lock, before g_seq fix) ===
cmd/load: same as Run 1
RESULT: ERROR SUMMARY: 13 errors from 2 contexts — all on `g_seq` (a
  monotonic ID-generation counter), read unguarded by h_meta's deal-seed
  loop (GameSlot.lock only) while written under g_registry_lock elsewhere.
  NOT Helgrind-clean.
FIX: g_seq changed to a C11 atomic_ulong (atomic_fetch_add_explicit /
  atomic_load_explicit, relaxed) — no lock needed, it has no other
  invariant to protect.

=== Run 3 (after both fixes; default pool sizes: game=6 meta=1 create=1) ===
cmd: valgrind --tool=helgrind --history-level=approx -- ./foolish_server 8098

RESULT: ERROR SUMMARY: 0 errors from 0 contexts (suppressed: 973308 from 187)
  — clean. Suppressions are valgrind/glibc's own defaults (pthread
