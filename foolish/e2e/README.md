# e2e - codified checks across the kernel, the client and the page

These run the **actual shipped code** in Node: the C kernel through the wasm
modules the browser and the tests load (`sdk/ts/wasm`), the client's
reconciliation and gates (`src/state`, `src/utils`), and the real page tree in
jsdom (`ServerProvider`, `GameView`, `Lobby`, `WinScreen`) with only its one seam
to the backend, `src/common/backend.ts`, stood in for by
`helpers/fake_backend.ts`, which serves real kernel-made envelopes and pushes.
Whole games run on the C Table in memory (`helpers/server_table.ts`,
`helpers/table_mem.ts`, `helpers/table_fixture.ts`).

There is no server here and no database.
The server is c_base, in C, and its tests are c_base's (`c_base/test`: the
routes through `cb_handle`, the stores on SQLite and DynamoDB Local, the push
stream over a real socket, and a smoke that plays whole games against
`cbase serve`).
Until stage 4 of `c_base/DESIGN.md` "Binary surface" this directory also ran the
TypeScript Supabase server against a real Postgres, in a second lane; that
server, its harness and the suites that tested it are in git history.

## Run

```bash
npm install
npm run test:e2e          # every file, the most expensive first
npm run test:validate     # the fast handpicked scenarios (e2e/validation)
```

### The expensive files start first: `e2e/FILE_ORDER`

The runner hands node:test a list, and node starts files in that order as slots
free.
The list used to be alphabetical, which is a scheduling decision nobody made on
purpose: the longest file sorted under "s" and started when the run was two
thirds done, with nothing left to overlap it.
So the runner reads `e2e/FILE_ORDER`, a plain-text list of every test file most
expensive first, and starts the files in that order.

The file is generated by `node scripts/run_e2e.mjs --write-order` and is never
hand-edited.
That flag preloads `scripts/e2e_order_probe.mjs` into every per-file child, which
asserts nothing and prints nothing; at exit it records the file's elapsed and CPU
milliseconds, and the runner writes the merged list when the run ends.
It is ranked on CPU time rather than elapsed.
Elapsed re-measures the contention of whichever run wrote the file - on a busy
machine it contains every second the file spent queued behind seven others for a
core - while CPU is the work the file actually did, reproducible across runs and
across machines.
Elapsed is kept beside it in the file so a reader can see which files are waiting
rather than working.

It is a hint and nothing else.
A file missing from it simply runs first (an unmeasured file may be the next long
one), a listed file that no longer exists is ignored, and a stale order costs
wall-clock and can never cost correctness.
The runner's header line prints how many files are unranked, which is how a
reader finds out the list has drifted behind the tree.

### Never `await import()` inside a loop

The suite's 27 minutes were not mostly gameplay, or Postgres, or the V8 coverage
instrumentation (that is ~20s of it).
They were module resolution.

Under the e2e runner's TypeScript loader a dynamic `import()` re-runs the whole
resolve hook chain on every call - about 1.9ms - even though the module is
already in the registry and nothing is re-evaluated.
A hoisted reference to the same module object is free.
`commitGame` alone lazily imported eight modules per move, `loadCompleteGame`
two, and `packed_review_gaps` five inside its per-move loop, so the fuzzers were
paying tens of milliseconds a move to look up paths they had already looked up
thousands of times.
`pass_parity` went from **357s to 14s** on that alone.

The dynamic imports under `e2e/` that remain are deliberate and must NOT be
hoisted: the page tests (`lobby_add_bot.test.ts`, `lobby_rules_box.test.ts`
and the others on `helpers/fake_backend.ts`) import *after* installing a
`mock.module`, and a static import would bind the real module before the mock
exists.

## Seeds

No suite draws from `Math.random` - `scripts/check_determinism.mjs` fails CI over
`e2e/`, `sdk/` and `server/` if one does, because the product's rule is one crypto
draw per game, at the deal, with everything after it derived from that seed.
A suite that shuffles unseeded breaks the same rule from the outside: every run is
a different experiment, and a red one hands the reader no repro.

Seeded suites draw from `helpers/rng.ts` (`suiteRng`), which resolves its seed as
`E2E_SEED_<SUITE>`, else `E2E_SEED`, else the fixed default, and prints the one it
picked.
The seed is named in the failure messages too, since that is the line that gets
pasted.

```bash
E2E_SEED_REPLAY_CODEC=12345 npm run test:e2e     # one suite, one experiment
E2E_SEED=12345 npm run test:e2e                  # every suite
for s in $(seq 1 50); do E2E_SEED=$s ... ; done  # widen the search deliberately
```

Seeding narrows nothing: the trial counts are what they were.

## What's checked

| file | asserts |
| --- | --- |
| `wasm_kernel_fuzz.test.ts` | hostile bytes at the wasm module's doors: no trap, no hang, no corruption of the flat linear memory |
| `pass_parity.test.ts` | pass legality agreed by the kernel, the table and the client's Pass button |
| `client.test.ts`, `client_*.test.ts` | the client's reconciliation, gates and rendered hand |
| `replay_*.test.ts` | the replay codec round-trips byte-exact, its extras, frames and links |
| `realtime_*.test.ts`, `lobby_*.test.ts`, `ui_*.test.ts` | the real page in jsdom on the backend seam: feeds and seating, spectators, the lobby's bot picker and rules box, DOM snapshots and the animation trace |
| `bot_roster_parity.test.ts` | the kernel's roster, the shipped module's dump and c_base's seeded bots agree |
| `security_client_boundary.test.ts` | nothing the browser loads can reach an unmasked game |

## What is not here, and where it went

A test whose every assertion is a question to the kernel belongs beside the kernel.
The table's moves on composed boards, the doors' refusals of impossible boards, the deck sizes and card conservation, and the cover resolver's fuzz were TypeScript files here that sealed a board over bots.wasm and asked `table_act` about it.
They are `c/tests/tests.c` now (`test_table_act_each_kind_of_move`, `test_table_act_refuses_forged_and_duplicate_attacks`, `test_table_cover_double_tap`, `test_table_deals_the_deck_and_random_games_conserve_it`, `test_unambiguous_cover_fuzz`, `test_table_load_refuses_a_board_it_could_not_have_made`), where they cost a fraction of a second and run under ASan.
What stays here is what C cannot see: the wasm crossing itself, a property of one wasm link (the shipped module's linked brains, its scratch overlays, its instance history), and the TypeScript and the page that read the kernel.
