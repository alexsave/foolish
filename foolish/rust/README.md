# rust/ - evidence against rewriting the kernel in Rust

> ## Read this first
>
> **This is not a migration. Nothing here is half-done, and nothing here is meant to be finished.**
>
> This directory is a *measurement*: four real kernel hot paths were ported to safe Rust once, benchmarked head-to-head against the shipped C, and then frozen.
> The ports are throwaway mirrors of `c/src`, hand-written to be bit-exact for the duration of one experiment.
> They are not a Rust kernel, not the start of one, and not a target anything builds.
>
> **The answer the experiment produced was: do not do the rewrite.**
> If you are a future reader - or a future agent - who found `rust/` and assumed someone was mid-port, stop.
> Nobody is. See [Why not](#why-not) below.

## What this is

`docs/RUST_VS_C_KERNEL.md` asked whether the C kernel should be rewritten in Rust.
The performance half of that question cannot be answered by argument, so it was answered by measurement, and this directory is the apparatus.

Four hot paths, each the real shipped C compiled straight out of `../c/src` at production flags, against a faithful safe-Rust port, over identical workloads generated by the real engine:

| bench | C under test | Rust port | workload |
|---|---|---|---|
| `legal` | `c/src/legal.c` `calculate_legal_moves` - runs on every action and every bot decision | `rs/src/bin/bench_legal.rs`, two variants: *faithful* (same bool tables) and *idiomatic* (u64/u16 bitmasks, same emitted order) | 20,000 decision states from 240 full games (2-8 players), dumped by `gen_states.c` driving the real engine |
| `playout` | `c/src/cordite_sim.c` `cd_sim_playout` plus the handwritten rollout policy - the Monte-Carlo hot loop of the shipped cordite/octogen bots | `rs/src/bin/bench_playout.rs`, engine in `rs/src/sim.rs`: full SimState bitboard engine including the game LCG | 600 of those states, played to completion with per-playout seeds |
| `solve` | `c/src/cordite_sim.c` `cd_sim_solve_d` - **octogen's dominant measured cost** (`sim_solve_rec` 36% plus `sim_gen_moves` 20% of instructions at 2p), at the shipped TT config (TT12, 2-way, packed 8-byte entries) | `rs/src/bin/bench_solve.rs`: full alpha-beta solver - fingerprint, TT probe/store on hand-packed u64 entries, movegen, per-node prefix clone | the deck-empty 2-players-IN endgame states (16 cards or fewer) from the same dump, 200k-node budget each |
| `wire` | `c/src/msg_wire.c` `msg_decode`/`msg_encode` - the iMessage FMSG envelope, the hostile-bytes parser | `rs/src/bin/bench_wire.rs` | 2,000 envelopes produced by the real `msg_encode`, 1 in 8 corrupted |

Every port is verified by checksum.
A Rust implementation has to reproduce the C output bit-for-bit before its timing is allowed to count, and for `solve` the checksum covers the value, abort flag and node count of every single solve, so all implementations are proven to expand the identical search forest.
The playout port carries the engine LCG and all the `double` math, and its checksums match the `-ffast-math -flto` clang build, the gcc build and Rust exactly.

That last point is the most interesting thing in this directory, and it is worth keeping even though the answer was no: bit-exact cross-language behaviour is achievable here, even for the float-bearing rollout policy.

## The numbers

Measured on the POC container: 4-core x86-64, Linux 6.18, clang 18 / gcc 13 / rustc 1.94.
Best-of-5 process invocations, best-of-3 for `solve`, best rep within each.

| bench | c-clang | c-gcc | rust (safe, faithful) | rust idiomatic |
|---|---|---|---|---|
| legal, ns/call | 417 | **384** | 477 (+14% vs clang) | 433 (+4%) |
| playout, us/playout | **1.41** | 1.62 | 1.59 (+13% vs clang, -2% vs gcc) | - |
| solve, Mnodes/s (higher is better) | **14.55** | 14.09 | 13.35 (+9% time vs clang, +5.5% vs gcc) | - |
| wire, ns/envelope | 734 | 746 | **700** (-5% vs clang) | - |

Struct sizes: `SimState` 328 B in C against 320 B in Rust from field reordering, `MsgEnvelope` 616 against 608, `LegalMoves` identical.
Peak RSS is workload-dominated and equal within noise on all three.

How to read it: three of the four deltas sit inside the gcc-versus-clang band measured on the *same C source* (legal +/-8%, playout +/-15%), and the direction of the delta flips per workload.
The solver is the one honest regression, and it is the one that matters most, because it is octogen's dominant cost - its inner loops are exactly the indexed-scratch code where bounds checks are paid and where `get_unchecked` would be needed to reach parity.
Even there the end-to-end effect is muted, because the solver is node-budget-capped per decision.

**Performance is a wash. It does not decide this question in either direction.**

## Why not

The recommendation is: **do not rewrite the kernel in Rust.**

1. **Performance buys nothing.**
   See above.
   The kernel also sits about two orders of magnitude below the plumbing in end-to-end cost, so even a real win would not be visible to a player.

2. **The C kernel is the single source of truth, and a rewrite forks it.**
   This is the reason that actually settles it.
   `c/src` is roughly 39 KLOC compiled, unchanged, to every place the game runs: the wasm rules and bots modules the web and edge functions load, the `Foolish.xcframework` static libraries the iOS and iMessage apps link, and the native C server under `server/impls/native/`.
   One implementation means one set of rules, one set of bugs, and one place to fix them.
   A Rust rewrite does not replace that on day one, it *duplicates* it, and the repo then owns two engines that must agree - across four deployment targets, a validation ladder, a replay format with live saved games in it, and a bot ELO table whose numbers only mean something if the engine underneath stays fixed.
   The repo has been through divergent-twin bugs before and the whole architectural direction has been to delete carriers, not add one.

3. **The wasm size discipline and the solver's frozen behaviour are the two things C is genuinely better at today**, and they are exactly the two things a port would have to touch last or not at all - which is another way of saying the port never actually finishes.

### The full analysis reaches a different conclusion, on purpose

`docs/RUST_VS_C_KERNEL.md` is the long-form examination, and it recommends a *phased* rewrite - server first, rules core second, bots last - on the grounds that the decision axis is correctness class rather than speed: it lays out a ledger of shipped memory-safety bugs, most of them compile-time-preventable in safe Rust, plus the ongoing fuzz/ASan/Helgrind tax that a safe language would subsume.
That argument is real and the doc is worth reading.

It was not adopted.
The fork cost in point 2 was judged to outweigh it, and this directory is the parked evidence rather than step one of the plan.
Read the doc for the reasoning on both sides; read this README for what was actually decided.

## Reproducing the numbers

The numbers above are frozen and were taken on a machine that is probably not yours.
Re-run before quoting any of them.

```bash
cd rust
make gen          # play 240 games through the real kernel, dump the workloads
make bench-c      # clang -O3 -ffast-math -flto, the production native flags
make bench-c-gcc  # same flags, gcc - this is what calibrates compiler variance
make bench-rs     # cargo --release: opt-level=3, fat LTO, 1 CGU, panic=abort
make clean
```

`make gen` and the `bench-c*` targets need only a C compiler.
`make bench-rs` needs a Rust toolchain, which this repo does not otherwise require and no lane installs.

Checksums printed by all implementations for a given (bench, reps) pair must be identical.
Timings are wall-clock best-of-N inside each process, and the reported figure is best-of-5 process invocations.

**A checksum mismatch means the Rust port is stale, not that you found something.**
The C halves recompile against the live `c/src`, which is the point of generating the workloads through the real engine - so kernel drift usually surfaces here as a build failure or a checksum change rather than silently.
The Rust ports do not recompile against anything, and they will drift.

Drift is not hypothetical, and it has already happened.
The `solve` bench expanded 46,894,219 nodes over 1,774 endgame states when the table above was measured; on today's `c/src` the same dump yields 1,810 states and 47,758,216 nodes.
The kernel moved.
The Rust ports did not.

## Build lanes

Nothing builds this directory.

- No workflow in `.github/workflows/` compiles it, installs a Rust toolchain, or names it.
- No other Makefile in the repo refers to it, and `rust/Makefile` is never invoked by one.
- No `package.json` script, product target or test reaches into it.
- Nothing in the repo depends on it, so deleting `rust/` would break nothing.

That is deliberate, and it should stay true.
If something here ever needs to be in a build lane, that is the moment to re-open the decision in `docs/RUST_VS_C_KERNEL.md` rather than to quietly wire it up.

The crate is still named `rustpoc` (`rs/Cargo.toml`) even though the directory is `rust/`, so that "poc" stays visible in every cargo invocation and build path.

## Layout

```
Makefile          the whole harness: gen, bench-c, bench-c-gcc, bench-rs, clean
gen_states.c      drives the real engine to dump states.bin + envelopes.bin
bench_common.h    checksum, workload loader, timing, RSS
bench_legal.c     C side, one per bench
bench_playout.c
bench_solve.c
bench_wire.c
rs/               the Rust side: crate `rustpoc`, one bin per bench
rs/src/sim.rs     the ported SimState engine that playout and solve run on
```

`build/`, `build-gcc/` and `rs/target/` are generated and gitignored.
