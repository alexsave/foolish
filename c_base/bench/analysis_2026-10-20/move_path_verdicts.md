## Double owners

- The game row is held encoded in four places that are each updated per move: the request's copy, the `kept` copy, the journal overlay (journal.c:207 jgame.row, the newest acknowledged), and the row cache (table_ops.c:81 g_cache, a copy of the same row with the same 256-entry LRU); cb_row_load reads the cache first and the overlay (via j_game_get) only on a miss, so two caches of the same bytes are kept warm per move, and a conflict drops only one of them (table_ops.c:703 cb_row_cache_drop; the overlay keeps its row).
- The row cache (CB_ROW_CACHE_CAP 256) and the overlay (OV_BUCKETS 1024, evicted only when idle 60 s with nothing waiting, journal.c:753) both decide what is "resident"; correctness relies on the version fence, so neither can be removed without the other becoming the one owner.
- The decoded Table in the per-thread section is a third form of the same game, rebuilt from the encoded row on every move.

## Answer 1: why removing SQLite did not lower CPU per move

- SQLite's per-move share was about 5-8 us of the 50 (sqlite3VdbeExec 2.8%, walChecksumBytes 1.4%, its fcntl/getpid/pwritev2 syscalls), and the journal path added back about the same: legal_moves_into + menu matching for the move index (new, 3-5 us), the bignum range coder (~1 us), the jrec row_dup + overlay swap (3 mallocs, 1.4 KB), the group-commit mutex and cond broadcast, and the flush thread still writing the same 1424 B rows to SQLite in the background (amortized but counted in the process's CPU).
- The 44% kernel time was never SQLite's: it is the loop<->worker hand-off (futex + eventfd write + eventfd read + epoll) and the send() per hearing socket, and the journal changed none of it.
- Everything else on the path (five pushes with 10 mallocs and 5 copies each, four row copies, five roster validations, 10 state_puts, 15-20 snprintfs, 500 strcmps in the row cache, the HMAC on vcache misses) is also unchanged, so the journal moved the floor of the write but not the walls around it.

## Answer 2: ranked verdicts

1. Run the move on the loop, no hand-off (design change, high value). Evidence: server.c:341-384 dispatch posts every /v1/action to the pool and the reply back by cb_loop_post, loop.c:272/:300 eventfd write + read, pool.c:93 futex wake; with one worker on the nano the pool buys nothing and costs two context switches per move. Saving: 10-15 us (most of the 22 us kernel), plus the task and post mallocs and 6 post_lock pairs. Steps: give /v1/action CB_ROUTE_INLINE (the inline_ok valve server.c:328 already guards slow handlers, and the journal removed the SQLite stall that justified the pool), and make local_deliver (rt_local.c:644) call pub_on_loop directly when already on the loop thread (no pub copy, no post, no eventfd), so the 5 pushes become 5 queue_frame appends and one send per socket at flush_dirty. Risk: a long bot drive holding the game lock (table_ops.c:461) would stall the loop; keep the drive on its own thread and have the inline path fall back to the pool when the lock is busy (pthread_mutex_trylock).
2. Make the JWT verify cache hit (quick fix). Evidence: jwt.c:70-84 VCACHE_N 32 direct-mapped per thread; auth.c:245 the HTTP path verifies per request; the rig's client sends a bearer per move (p3load3.c:77). Saving: 3-6 us per move under load (the HMAC + 2 base64 + the re-encode compare, OpenSSL 3's EVP fetch included); ~0 in production with few players. Fix: key the cache by the session id already held live (auth.c live table) or make it 1024 entries 2-way; or move the clients to SF_REQ over the socket where auth is a struct copy (auth.c:246).
3. One owner for the game row: the overlay is the cache (design change). Evidence: table_ops.c:81-147 g_cache with cache_find's 256 strcmps twice per move (:91), four row copies per move (:58, :696, journal.c:916, table_ops.c:127), cb_row_cache_note after a commit the overlay already holds. Saving: 8-9 mallocs + 3 x 1.6 KB copies + ~500 strcmps + 2 mutex pairs = 4-6 us. Fix: delete g_cache, have ov_get return the row under the game lock without row_dup (the lock already serializes a game's commits), and let the kept row be the overlay's.
4. Stop coding the move by menu index on the hot path (quick fix). Evidence: table_ops.c:897-899 replay_move_of -> replay_move.c:42 legal_moves_into + a linear match; the journal already has an escape (index == menu_n carries the awire bytes, replay_move.h wire[]) and recovery replays through replay_move_wire. Saving: 3-5 us (the whole menu enumeration; legal.c:236-290 is exponential in matching cards). Fix: always code the escape (a few bytes more per 16 B batch), or compute the menu only when a bot cycle needs it.
5. Replace snprintf and the roster re-validation with length-known copies (quick fix). Evidence: seat_id (table_ops.c:321) and section_row/fanout snprintf (:546,:583,:662,:683, fanout.c:112-118, journal.c:913); roster.c:280 roster_validate per trailer, :150 the canon re-encode + bytes_eq byte loop in every decode. Saving: 3-4 us (printf_core 1.2% + the roster.c 1.4%). Fix: memcpy with id_len; validate once in roster_decode and pass a "validated" Roster to the trailer writer; compare the canon with memcmp.
6. Remove dead work (quick fix, ~2-3 us): the actor envelope dup freed unread (table_ops.c:689 -> functions_http.c:150); the spectator envelope and cast when no room is watched (ask the hub, or build lazily); RAND_bytes on every move when only a deal uses the seed (table_ops.c:898, move it into the deal path); the 1227 B roster memcmp (table_ops.c:619) replaced by c->roster_changed; buf_idle freeing c->in/c->out per request (server.c:70, keep them on keep-alive sockets).
7. Build each push frame once into the socket's out buffer (design, 1-2 us): pushes.c:32 cb_buf + rt_local.c:658 pub copy + server.c:423 queue_frame are three copies and two mallocs of the same bytes per push; with verdict 1 the frame can be encoded straight into c->out.
8. Log hygiene (quick): log.c formats before the level check and takes g_lock; bots.c:114 writes an INFO line (a write syscall) per bot cycle; gate on g_min first, demote the cycle line.
9. Bot-game kick (quick, bot games only): bots.c:410 kick_wanted does a SQLite lease_held SELECT per human move; use the in-memory lease under serve.
10. Zero less in cb_section_free (table_ops.c:264-274, ~1 us): zero only the fields table_init/table_load overwrite anyway, keep the arena_hw prefix memset.

## Answer 3: the path to 1-2 syscalls per move

- Today (HTTP + pool): recv, futex wake, eventfd write, eventfd read, send (response), one send per hearing socket, futex wait: 8-10.
- Step 1 (verdict 1, inline on the loop): drops the futex wake/wait and the eventfd write/read: 1 recv + 1 send (response) + h sends (one per hearing socket, mark_dirty already coalesces a socket's view and cast into one send, server.c:518-530) = 4 for 2 humans.
- Step 2 (clients send the move as SF_REQ over the socket, rt_local.c:316 run_req): the actor's REPLY and its own view + cast share the actor's socket, so flush_dirty writes them in one send: 1 recv + h sends = 3 for 2 humans, 1 + 1 for a solo bot game; this is the floor without batching across connections (each hearer is its own socket, so one send per hearer is irreducible on plain sockets).
- Step 3 (io_uring): one io_uring_enter per loop iteration submitting the recv re-arm and all pending sends (and multishot recv), so a move costs 1 syscall shared across every socket touched in the iteration, or 0 with SQPOLL (which burns a core the nano does not have). Blockers: the loop is epoll-shaped (c_base/core/src/net/poller.c, loop.c:351 one callback per ready fd) with buffers owned per conn and freed by buf_idle, so it needs registered/fixed buffers and a completion-driven conn state machine; the Alpine/musl static build (c_base/bench/nano/build.sh:11) has no liburing, so the ring would be hand-rolled over the raw syscalls; and inline dispatch (step 1) must land first or the hand-off dominates again.
- Independent of all three: the journal already costs 0 syscalls per move, so the store is not on the syscall path at all.

## Answer 4: a decoded Game in the overlay instead of the encoded row

- What it removes per move: table_load (roster_decode with its canon re-encode and 1227 B compare, state_blob_load, table_seat_kinds), the row's state_put + roster_encode in commit_products (table.c:376/:384), and three of the four row copies with their 6-8 mallocs; about 5-7 us, 10-14% of the move.
- What it does not remove: the per-viewer envelopes and casts (state_put per viewer and per event is the client wire format and stays), the fan-out copies, the hand-off, the HMAC, the menu enumeration; so it is below verdicts 1-4 in payoff and should ride on verdict 3 (one owner) rather than be done alone.
- Cost: a Game is ~37 KB of which 36 KB is the MAX_LOGS array (game.h:223; the journal already keeps each move's log delta, journal.c:333), so a resident game needs a Game without the log array plus the Table (Roster ~1.3 KB, clock, ratings): ~2-3 KB per live game against 1.5 KB for the row; 1000 live games fit the nano either way, but TableSnaps (64 KB, table.h:161) must stay per thread, not per game.
- Risk: table_act mutates the board in place and a REJECTED apply (table.c:131) leaves the Game as awire_apply left it, so a resident game needs copy-on-apply (memcpy the ~1 KB non-log Game into the section, apply, swap on commit), which is still 50x cheaper than the decode; the rows must still be encoded for the flush (journal.c:734 cb_rows_sql_flush), the backup and game_get from other paths (views, bots), so the encode moves to those points (once per flush instead of once per move); and the section's zero-state contract (table_ops.c:168-180) becomes the resident game's invariant.
- Verdict: worth doing, about 10-14%, as the second half of verdict 3; not the first lever.

## Why human pace costs more per move

Read-only analysis of scratchpad/qw/quick_rig.txt, ec2_all.txt, ec2_all2.txt and the code on main a3bd21b14 plus branch quick-wins (worktree /Users/alex/Dev/foolish/.claude/worktrees/quick-wins).
Rig numbers come from `play_cpu_s / moves` where play_cpu_s is the process's utime+stime ticks sampled at 100 Hz between t_go and t_done (c_base/bench/nano/summ.py:67-88, sampler.sh); Graviton numbers are perf stat task-clock over a 10 s window opened 8 s after release (q.sh-style `pre`), divided by the window's moves.

### What the two paces actually run

- At human pace (q.sh `hum`: 192 pairs, 2-4 s think, PLAY_CPUS=0.1, 30 s) every pair, right after `go`, does a create, a join and a start (p3load3.c:388-396 submit NC_DO_CREATE / submit_ask(ASK_JOIN); :202 submit_ask(ASK_START)), three non-plain commits that each write SQLite synchronously under the game lock (journal.c:875 around -> cb_rows_sql_flush), plus two SUBs; then the moves: 2690 moves in 27.9 s on the rig, 14 per pair; no game ends (games_over=0).
- At saturation (q.sh `sat`: 8 pairs, no think, PLAY_CPUS=1.0, 20 s) the same three commits happen once per finished game (3666 games over 416k moves: once per 113 moves) and the finalize (replay encode + snapshot_put) once per 113 moves too.
- Moves travel as SF_REQ over the socket (foolish/c/src/netclient.c:1195-1196, :1728 sf_put_req for POST /v1/action), and pump (rt_local.c:474) ALWAYS submits a socket request to the pool: there is no inline path for socket moves (inline_ok, server.c:328, is HTTP-only). So every move is loop -> worker -> loop.
- At saturation the worker never sleeps (pool.c:47 finds a task queued), pthread_cond_signal has no waiter (no futex syscall), and the loop's eventfd write is coalesced by wake_pending (loop.c:288) across the dozens of posts of one pass; at human pace each move is one futex wake of a sleeping worker, one futex wait when it finishes, one eventfd write (all the move's posts share it), one eventfd read, and two epoll_wait returns (the recv, then the eventfd).
- Syscalls per move confirm it: Graviton J4 h192 9981 syscalls / ~973 moves = 10.3, J4 sat 3.05M / 138k = 22 (the saturation run also carries 10% refused moves, game ends, creates, joins and finalizes); rig 9338 / ~965 = 9.7 at human pace.

## Final rig, preliminary

Read-only analysis of scratchpad/final/results.txt (round 1 of 3), matrix.sh, fr.sh, fin.py, and the code in scratchpad/final/wt_now (main 4aa1c22e3) against wt_base (5d5ef505b).
Rig: Docker arm64 on a Mac, one request worker, PLAY_CPUS=1.0 at every scenario (fr.sh:2-3), so the human-pace absolutes carry the host's low clock (see "Why human pace costs more per move") but BASE and NOW are measured alike.

### What the window measures (fin.py)

- CPU, syscalls, moves and latencies are windowed: human pace from 500 ms after the last pair's first move to 2 s before the deadline (fin.py:64-65), saturation from 6 s after go (fin.py:4); the window is snapped to perf's 1 s intervals; cgroup and perf agree within 3-8% everywhere, so the CPU numbers are sound.
- Three per-move byte figures are NOT windowed: `journal_B_per_move` and `wal_B_per_move` come from the server's close-time log line (fin.py:141-142 regex on "journal: N record(s) ... M byte(s) ... K WAL frame(s) before the close's flush"), whose WAL meter is the SQLite connection's lifetime frame counter (store_sqlite.c:148 wal_frames, :416, read at journal.c:2159), divided by the whole run's applied moves; `disk_B_per_move` is sectors written from release to after the shutdown and `sync` (fin.py:135), so it includes the close's flush of every waiting move.

### 1. RSS: 67-71 MB at sat2 and 45-50 MB at sat8 versus 14-16 MB

- The overlay holds every waiting move's log delta until a flush: j_game_commit dup_bytes the delta (wt_now journal.c:1557) and ov_apply appends it to the game's move list (:500), where it stays until the flush rule fires: game_age_ms 600 s (foolish_app.c:97), game_bytes 256 KiB per game (:98), total_bytes 64 MiB (:99).
- At sat2 the run applied 523,838 moves across 192 games; move_bytes is sizeof(cb_game_move) + len, about 60-70 B per move (journal.c:240), so the waiting set reached ~33 MB of payload, under the 64 MiB total and under 256 KiB per game (2,700 moves per game x 65 B = 175 KiB): nothing flushed during the run, exactly as the rule says. With musl's 16 B header and size-class rounding the ~50 B log delta costs a 64 B slot, so about 45-50 MB of anonymous memory is the waiting log deltas, plus the 192 residents (2.5 KB + grown row buffers, ~1 MB), the move arrays (24-32 B per move, ~15 MB counted above), the 128 spare 32 KB buffers (server.c:78-79, up to 4 MB), one 8 MiB mapped segment's touched pages (file-backed shared pages count in VmRSS; finished segments are munmapped at seg_finish journal.c:555-557 and the next segment is fallocated but untouched), and the per-thread sections (loop + 1 worker + the job pool, ~320 KB each).
- sat8: 431,545 moves over 48 games: per game 9,000 moves x 65 B = 585 KiB, over game_bytes 256 KiB, so each game flushed roughly twice (wal_B 412 x 431k = 178 MB of WAL confirms flushing); RSS 45-50 MB is the same waiting set bounded by 48 x 256 KiB = 12 MB of payload plus the current segment, buffers and the finalize job's 3.25 MB (table_ops.c:467-480, freed per job; musl unmaps allocations that large, so no retention).
- So: real anonymous memory, by the flush rule's own caps, not a leak; BASE had none of it because every move went straight to SQLite. It is also worst-case: saturation fills 64 MiB in 30 s; at production pace the 600 s age flush bounds it at (moves per 10 min) x 65 B.
- Fixes: (a) hold the deltas in one grown buffer per game instead of a malloc per move (the cb_game_move array keeps offsets): removes the 16 B header and the size-class waste, ~35% of that memory, and one malloc/free pair per move (quick, journal.c:500/:1557); (b) lower total_bytes to 16 MiB or add a count cap (e.g. 2,000 waiting moves per game) so the nano never holds 64 MiB of logs (quick, foolish_app.c:97-99); (c) the segment ahead could be made at seg_bytes/4 and grown (no RSS effect, only disk) - skip.

### 2. WAL and journal bytes at human pace

- WAL 4,666 B/move at hum2 = 4,725 frames x 4,120 B over the whole run (19.5 MB), and 7,184 B/move at hum8 = 23.6 MB. Both runs have games_over=0 and game_age_ms is 600 s, so no flush ran during play; O-4 sends deals, joins and lobby edits through the overlay as R records (journal.c:32 FULL_MAGIC), so no commit wrote SQLite either; the only SQLite writes are the sign-up phase before `go`: 384 accounts at hum2 and 528 at hum8 (48 x 8 players + 48 x 3 spectators), each a users row, a sessions row and a ratings row in separate transactions with their index pages, 10-12 frames per account: 384 x 12 = 4,600 frames and 528 x 11 = 5,800 frames match 4,725 and 5,730. The WAL at human pace is the sign-ups divided by the moves; the lifetime meter is the artifact (fin.py:141-142). Fix: read the meter at `go` too (a `store: wal:` line or the WAL file size at release) and difference it; or print the meter in the admin stats and sample it with cgsamp.
- Journal 217 B/move at hum2 = 905 KB over 4,171 moves: the 192 pairs' setup is 3 full records each (create, join, start: 576 R records), and an R record carries the game id, the versions, log_from, the seed, the whole state blob and the whole 1,227 B roster plus the deal's log (full_decode journal.c:704-754): about 1.5 KB each, 864 KB in all; the 4,171 moves at ~10 B are the remaining 42 KB. hum8 329 B/move: 48 x (1 create + 7 joins + 1 start) = 432 R records at ~1.7 KB (8-seat state, 8 hands in the deal log) = 740 KB + 3,286 moves x ~20 B = 66 KB ... the measured 1.08 MB suggests ~2.3 KB per R record at 8 seats (the deal's log records every dealt card). At saturation the same per game amortizes over 75-113 moves: 59 B/move = ~16 B per move + ~4.5 KB of R records per game. So the design's 16-20 B per move holds for moves; the human-pace figure is setup R records over few moves, and the window is not catching setup for CPU but these byte figures are whole-run.
- disk_B 1,423 B/move at hum2 is the close's flush (5.9 MB: every game's row and its log items written once at shutdown, fin.py:135 counts to after the sync) over the run's moves; during play the only disk writes are the segment's dirty pages written back by the kernel (a few KB per 5 s) and the server log.
- Fixes: (a) windowed byte meters (quick, fin.py); (b) a smaller R record: the roster is 1,227 B whatever the seat count (roster.c _Static_assert "the roster is 1227 bytes") and a join changes one seat; coding the R row with roster_encode's used prefix (2 + title + n x 128 B) cuts a 2-seat record to ~450 B, a kernel-side variable-length encode behind the same decode (design, roster.c:106 and journal.c full encode); (c) at production pace neither matters: a game writes 3-9 R records (5-15 KB) once.

### 3. Saturation: 45 us at sat2 here versus 26 us in the inline agent's check

- Different scenario: fr.sh sat2 is 192 pairs (384 sockets, 192 live games, lcpu=5 load containers), the quick checks were 8 pairs (q.sh/meas.sh "8 two-seat games, 1 CPU"); at 192 games the resident set, the socket table and the per-pass event batches are larger, and five load CPUs contend with the server's vCPU for the Mac's cores, so the server runs slower per instruction than in a 1+1 setup.
- Game churn in the window: 4,671 games over in the run (one per 75 moves at sat2 vs one per 113 in the 8-pair check), each costing a finalize job (table_replay_code re-runs the whole game plus table_replay_extras plus a snapshot_put transaction, 3.25 MB of mallocs, table_ops.c:467-494) and 3 R records; at 300-900 us per finalize that is 4-12 us per move, and the finalize now runs on the job pool, so it is on the clock without being on the move path.
- Refused moves: 25,148 of 352,059 in the window (7%), each a full request (recv, parse, adopt, apply, refusal reply, send) at ~20 us with no commit: ~1.5 us per move.
- TCP RX softirq is charged to the task at saturation (the earlier Graviton profiles showed handle_softirqs at 5-6% only at saturation): ~3-5 us.
- Where the rest goes (by the code path, no profile in this round): recv ~2-3 us; one epoll_wait per pass (<1 us per move); handler: adopt 2.5 KB, apply, table_commit_products (state_put x3, roster trailers, log records), 3 casts (evwire_serialize each) ~6-8 us; the journal record and the resident swap ~2 us; 5 frame encodes and queue_frame copies ~2 us; two to three send()s at 3-5 us each in the VM ~10-13 us. That sums to 35-45 us with the churn, matching 45. The move path itself is roughly 25 us; the other 20 are sends and game churn.

### 4. hum8 costs 3x hum2 per move

- Per move hum2 publishes 2 views + 2 casts + 1 spectator cast to 2 sockets (the actor's reply rides with its own pushes): 2 sends; hum8 publishes 8 views + 8 casts + 1 spectator cast to 8 players + 3 spectators: 11 sends (syscalls 12.5 vs 4.0 per move say exactly that).
- Per hearer the server builds one envelope (state_put + roster trailer, table.c:402-412) and one cast (evwire_serialize: one state_put per event plus the final snapshot, per viewer, table.c:286), encodes two frames, copies them into the socket's out buffer, and does one send(). (221 - 74) / (11 - 2) = 16 us per extra hearer on the rig; of that the send() is 5-8 us (the VM's TCP path), the cast 2-3 us, the envelope ~1 us, the frames and copies ~1 us, and the pub lookups (rt_local.c pub_on_loop: user bucket walk, cb_server_wake scan) ~1 us. The 8-seat board also makes more snapshots per move (a round with 8 players has more events), so even the actor's own cast is bigger.
- Irreducible part: one send per hearing socket; io_uring batched the 11 sends into one enter (2.01 syscalls per move at hum8) and saved nothing (219 vs 221 us), so the cost is the TCP work per segment, not the syscall entry.
- Reducible part: (a) the spectators' cast is one buffer sent to 3 sockets, fine; the 8 players' casts differ only in card masking: evwire_serialize could emit the shared event skeleton once and patch the viewer-specific card bytes, saving ~70% of 8 cast builds (~10 us at hum8): a kernel change (evwire.c) behind the same wire; (b) the view push is redundant with the cast for a client that applies casts (the netclient's web model applies casts; the view is the fallback): sending the view only to sockets that asked for views would halve the frames per hearer (~2 us per hearer): protocol-visible, so the clients must opt in; (c) smaller frames: the envelope repeats the roster trailer per push (~150-250 B x 8).

### 5. io_uring: half the syscalls, no CPU saved, a little latency added

- The backend (c_base/core/src/net/uring.c) submits the pass's sends as IORING_OP_SEND SQEs and does one io_uring_enter with GETEVENTS and a timeout (uring.c:168-186), so recv readiness, sends and the wait share one enter per pass: 1.96 syscalls per move at hum2 (the enter plus one recv), 2.01 at hum8 (eleven sends in one enter).
- No CPU saved because a syscall entry on this VM costs ~0.3-0.5 us while the work the syscall does (tcp_sendmsg, skb allocation, the virtio/ENA transmit) is unchanged, and io_uring adds its own: an SQE and CQE per send, the kernel's io_issue path and task_work on completion, and the user side's completion walk; at 11 sends per move that overhead is a wash against 10 saved entries.
- Latency: a send is now issued at the next enter instead of inside flush_dirty, and its completion (and the out buffer's release) is seen one pass later; p50 move latency moved 0.139 -> 0.149 ms at hum2 and p99 31 -> 34 ms at sat2, consistent with one extra pass of queueing.
- Verdict: leave it off on the rig; it is worth re-testing only on Graviton, where syscall entry/exit carries the arm64 mitigations and the ENA path differs, and where the earlier profiles showed el0_svc at 1.5-2% and __arch_copy_from_user at 1.5% (the copy stays either way). Expect at most 2-4 us per move there; keep it behind the flag.
