§2 · the map

The whole repository on one map

Columns are products. Rows are layers, from people at the top to the outside world at the bottom. shared/ sits beside foolish because every product leans on it.

Each box is one thing in the repository, and the status is written on it: PARKED, PLANNED, PROOF OF CONCEPT or OUTSIDE THIS REPO. Boxes without a tag are live in the tree. Each line says what it is: grey lines are requests at run time, blue lines are builds and generated code, gold lines are deploys, green dashed lines are tests, and dotted lines are planned or parked.

§4 · kernel

One kernel, and what is generated from it

foolish/c/src is the one implementation of Durak. The foolish README counts four build trees that compile the same files: c/Makefile for native binaries and differential suites, the iOS xcframework, foolyard/, and rust/, which it describes as frozen and built by nothing. The backend links the kernel natively. Browsers load it as WebAssembly.

ModuleUsed bySize and notes
web.wasm.gzthe website, through sdk/tsExport allow-list, so the bots and the C table are dropped by the linker.
promo.wasm.gzthe promo page at /brA local table and one bot. No backend client.
oracle.wasm.gzthe replay analyser (Mode A)177,835 bytes raw. Used only by the replay analyser.
oracle-mt.wasm.gzthe same analyser, shared-memory build (Mode B)1,091,163 bytes raw. Behind a cross-origin flag that is off by default.

Generated code is never committed. structgen reads struct layouts through libclang and never reads values. datagen reads table contents and never reads layouts. Every wasm and iOS module is compiled with a hash of its own struct layout, and the host refuses a mismatch on first call.

The toolchain is pinned to clang 22.1.8 and binaryen 130. With that pin, the raw module is byte-identical on macOS arm64, Linux arm64 and Linux x86_64. That is why wasm_build.sh --check can build twice and refuse a difference.

c/src/bot_roster.c is the single table for what a named bot is. The backend's seeding, the iOS bridge and the wasm all read it. The ladder players meet has ten rungs. The README counts 21 bot strategies in all.

§5 · server

The server: a platform and an app on top of it

The platform exists twice. The public cbase repository is the newer one. c_base/ in this repository is an older copy, and CI builds it into the production binary. Both hold the HTTP server, the store, auth, the push stream, the admin console, backups and the providers. foolish/server/ is Foolish on top: the routes it answers, table operations, bots, fan-out and pushes.

In production one process runs on one VM, in an autoscaling group of one. It takes an exclusive lock on its database when it boots, so a second server on the same file refuses to start. Commits use a compare-and-swap on the game's version. Bots are driven by commits and by a scan every minute, not by timers.

Routes

RouteCarries
/v1/auth/signup, signin, refresh, signout, passworda session in a binary body, or 204
/v1/create, /v1/action, /v1/metathe kernel's own bytes in, and the caller's view or the kernel's 7-byte response out
/v1/gamesevery view the caller has, newest first
/v1/games/{id}the caller's view if seated, otherwise the spectator view
/v1/chat/{id}GET the newest 100 messages; POST one message of 1 to 1000 bytes, members only
/v1/bots, /v1/leaderboard, /v1/history, /v1/replay/{id}the bot list; the top 100 humans and bots; your rating and replays; one replay
/mqttMQTT 3.1.1 over WebSocket, subprotocol mqtt, carrying push frames
/admin, /healththe admin console behind a Bearer token; a health check

Every route under /v1/ refuses in one format, so no client matches on a server message. The two read routes that answer the same to everyone are cached at the edge: the leaderboard for an hour, and the bot list for a day. Both are invalidated when the thing they show changes.

Push topics

TopicCarries
u/{user}/vyour views, when a game you play changes
u/{user}/c/{game}the casts of a game you sit in
s/{game}the spectator view of a game
u/{user}/m/{game}the chat of a game you sit in

A connection may subscribe only under its own user and under s/. Nothing may publish from a client.

Backups and providers

The database is copied to S3. A restore fills a missing database and never overwrites an existing one. Three providers exist for the platform. local (SQLite on one VM) is the one in production. aws (Lambda, DynamoDB, IoT Core) served foolish from 2026-10-14 to 2026-10-19 and is not in production now. gcp is an unbuilt slot.

§7 · build, deploy and proof

Build, deploy and proof

There are 17 workflows. Each runs from its own product folder and triggers only on that folder and on shared/.

The deploy lane is the deploy job in c_base.yml. On main it runs ./cbase deploy from the cbase submodule. Deploys queue, so the newest commit on main always ships and two deploys never overlap. The job dry-runs unless the repository variable CBASE_DEPLOY is set. Its role can make only the calls that deploy makes.

  • e2e: 198 files. Runs the shipped kernel wasm, the client code, and the page in jsdom. No server and no database.
  • C: 200 tests in one binary, three differential suites, and an ASan build.
  • Derived gates: 17 tests that walk the repository and assert about it. For example, generated files must match the C, and the Apple domain file must name the Team ID the project signs with.
  • Backend: make check, coverage floors, and a nightly fuzz workflow.
  • Apple: 847 Swift tests. They run on a Mac by hand, because macOS CI minutes bill at ten times the Linux rate.
  • foolyard: a deterministic single-threaded simulation of the server, clients and wires, with the real kernel deciding every rule.
§8 · the public repositories

cbase, cdom and amgi, read in full

Three public repositories sit under this one. Each is mapped at the subsystem level in its own lane of the map. I read the code and docs of each, not only the README.

cbase: the platform

cbase is one C program. cbase serve runs the HTTP and WebSocket server, its own MQTT hub, auth, jobs, the admin console and a SQLite store. A product links its own code in as a separate binary. Providers are chosen at link time: local (SQLite on one VM) and aws (Lambda, DynamoDB, IoT Core).

  • Server. The router takes exact, prefix and parameterized routes, and runs each handler on a request pool, on the loop, or on a slow pool for remote calls. The store has a single interface with a backend per provider, and writes finish before their response. Commits are compare-and-swap on a version.
  • Security defaults. CORS is denied unless listed. Request bodies are capped at 1 MiB unless a route sets its own cap. The settings file is read strictly.
  • Clients. One sans-IO C client core that allocates nothing, with hosts for POSIX, wasm with TypeScript, and cdom. The Swift client has its HTTP half only. The cdom host is the one place cbase depends on cdom.
  • Deploy. The tools/cbase launcher builds a C deploy CLI on first use. It creates groups, deploys static sites and app VMs from cbase.conf, handles certificates, and has the safety rules. Its README describes the deployment shape: one VM group with a systemd service and port per app, and one static bucket, behind one CloudFront distribution per app.
  • History. Lambda and DynamoDB served foolish from 2026-10-14 to 2026-10-19. The VM has been production since then. The DESIGN doc keeps that history.
  • Status. Version 0.1.10, pre-1.0. Foolish pins c8f83cd9, and cbase HEAD is 2575a2d. This checkout does not contain the submodule files.

cdom: the UI library

cdom lets C own the DOM. The tree, the state and the keyed diff live in C in WebAssembly memory. A fixed JavaScript shim makes one DOM call per operation and posts events back. The shim is about 15.7 KB minified, and an app's module is in the tens of kilobytes.

  • Core. cdom.c holds the tree, the string table, and the keyed list. The program's libc comes from cdom, with memcpy and memset mapped to bulk-memory builtins.
  • Platform modules. net (HTTP and WebSockets), store (IndexedDB), audio, fonts, share, url, locale and random. Each is opt-in. Random comes from one seedable source.
  • Contract. The API in cdom.h changes only additively. A link test fails to compile when a call changes in place.
  • Build. An app's Makefile includes cdom.mk for the flags, sources, wasm rule and page rule. Node is not needed to build an app. A legacy wasm2js path is opt-in for browsers without WebAssembly.
  • Dependency rule. cdom never names cbase. Its own tools/edges.mjs fails the build if it does.
  • Measurements. Compared with vanillajs and React 19.2.0 on js-framework-benchmark, on an Apple M1 on 2026-10-27. Bridge alternatives were measured on 2026-11-01 and not adopted.

amgi: speech flashcards on Anki

amgi writes Anki cards with spoken audio into the user's own collection. Anki does scheduling and sync. amgi generates the card text and the clip with Gemini, checks each clip by transcribing it back, and ships an Anki card template where the prompt plays and the microphone opens by itself. There is no hosted backend and no login. The key stays on the user's machine.

  • Server. A C program linked into cbase serve. Its routes live under /api/anki: decks, notes, card text, audio, install, starter and media. Gemini is called over gRPC from C, using cbase's HTTP/2 and gRPC code. A rate gate refuses a start before any work begins.
  • Two ways into Anki. When Anki is closed, the server opens the collection file itself through a C port of Anki's note and deck rules. When Anki is open, a Python add-on inside Anki answers over a local HTTP bridge. The bridge checks a protocol number on each request. A backup runs before every write, and the server refuses any collection with a -wal or -shm file beside it.
  • UI. C on cdom, with its own wire layout. It does not use cbase's client SDK.
  • Earlier code. The Node implementation of the card policy is still in plusaudio/. The add-on runs it through generate-clip.js, and the server holds a C port of the same policy.
  • Incident 1842. On 2026-11-08 Anki's backup-on-close dropped its own lock while Anki kept writing to its -wal. A second connection then checkpointed Anki's live WAL, and the collection file was zeroed. The rules above, and a test that is red without the -wal rule, came out of it.
  • Pins. amgi pins cbase at 352658cd and cdom at 386cc824. Those are different from foolish's pins.

The cutover

CUTOVER.md, dated 2026-11-09, says ./cbase adopts the live setup. It moves foolish, utils and uttt onto three cbase-app-* stacks, with DNS unchanged and one downtime window. The old distributions stay as the rollback. This pass read the repositories and the pins, not the AWS account, so I cannot say whether those steps have run.

§9 · open items

Open items, and what this map could not check

  • Two copies of the platform. c_base/ in this repository is what CI builds into production. The public cbase repository is newer, and 119 core files differ. Pick one as the platform of record before the cutover, which assumes the submodule.
  • Three pins. foolish pins cbase c8f83cd9 and cdom is not pinned by foolish at all. amgi pins cbase 352658cd and cdom 386cc824. cbase's own adapter pins cdom f00157c0. Decide which set is supported.
  • c_base/README.md says Lambda and DynamoDB are in production. They are not, and have not been since 2026-10-19. Correct the README, and retire or label c_base/RUNBOOK.md, which still describes the Lambda deployment.
  • foolish/README.md cites c_base/src/store/store.c. Point it at c_base/core/src/store/.
  • uttt/README.md says nothing is built. Update it to match the tree.
  • amgi/plusaudio/ is the old Node card policy, still run by the add-on. Retire it once the add-on calls the C server.
  • pickemup: the extension is built but has not been seen inside Messages, per its own orchestration notes.
  • Not checked: live AWS state, App Store status for each product, whether the cutover steps have run, whether uttt.live is serving, and whether amgi's pins are the current heads of cbase and cdom. The public clones were shallow, so history older than their heads was not read.
