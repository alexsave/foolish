## 0. Read this first: two security findings made while planning

These are not part of the refactor, but they sit on the tables it rewrites and they look live, so they come first (Phase 0.1).

1. **`commit_game` has probably been callable by `anon` on the hosted DB since migration `20260906120000`.**
   `server/impls/supabase/migrations/20260906120000_drop_json_hand_columns.sql:53-55` runs `DROP FUNCTION commit_game(...)` and then a plain `CREATE FUNCTION commit_game(...)` with `SECURITY DEFINER` (`:70`).
   A newly created Postgres function is executable by `PUBLIC`, and nothing in that file re-runs the lockdown loop from `20260807120000_lock_down_state_rpcs.sql:23-43`.
   `seed.sql:759-778` does re-run it, and `e2e/db_grants.test.ts` only ever sees `seed.sql`, so CI is green while the migrated database is open.
   With the anon key (it ships in the web bundle) and a game id plus its `version` (both in the `games` column grant, `seed.sql:269-273`), anyone could overwrite any game's state, roster and views.
   The owner should confirm with one read-only query: `select has_function_privilege('anon', 'commit_game(text,bigint,jsonb,jsonb,jsonb,text,text,boolean,text,jsonb,text,boolean)', 'execute');`.
2. **`games` probably accepts direct INSERTs from any authenticated user.**
   `seed.sql:275-278` has the policy "Authenticated users can create games" and only SELECT was revoked (`seed.sql:268`).
   Supabase's default privileges grant INSERT on public tables to `authenticated`, so a client can insert a row with a fabricated `players` roster and `state` blob, then drive it through the `action` endpoint (`packed_action.ts:127` takes the seat from that JSONB) to a finish that `finalizeEndedGame` scores into other players' ELO.
   Nothing in the app inserts into `games` with a user token (`create` uses the service role RPC, `create/index.ts:78`).

Also found, smaller and lobby-only (Phase 3 fixes them by construction, Phase 0.2 pins them):

3. `meta type:'exit'` removes whoever `body.player_id` names and never checks that the caller is seated (`meta_actions.ts:142,161-165`); `add-bot` never checks the caller either (`meta_actions.ts:72-137`).
   The web uses the first as a lobby "remove player" feature (`src/components/Lobby.tsx:440-444`), so the policy needs a decision (section 6, Q9), not a silent change.

## 1. Goal, non-goals, fixed decisions

### Goal

The C kernel owns the whole shape of a game everywhere in this repo: the board (`Game`), who sits where (a new `Roster`), every byte layout that crosses a boundary, and every rule including the player_id to seat mapping.
TypeScript ends up knowing neither byte layouts nor the game shape.
Where TS must touch a C value it goes through modules generated by `tools/structgen` from the real wasm32 layouts.
Hand-written TS is left doing only what C cannot: HTTP, auth, database calls, realtime, timers, React rendering, and moving opaque bytes between those and the kernel.

### Non-goals

- Redesigning iOS.
  iOS keeps working through the same wires; its own Swift decoders are left alone (see 5.4 and Q13).
- The iOS spectator feed (already deferred, `fd6e5955`).
- Changing gameplay, bot strength, the replay formats, the FMSG/iMessage wire, or the animation catalogue.
- Deploying anything, pushing, or touching the hosted database.
  Deploy points are marked for the owner; every phase is verified locally and in CI only.

### Fixed owner decisions (not relitigated here)

- Scope is everything: server, web client, SDK, DB, tests.
- C over TS wins over speed and size, but generated TS must stay small and fast, and both are measured per phase.
- The player_id to seat mapping moves into C.
- DB migrations are allowed (supabase CLI); no deploys, pushes or hosted-DB operations.
- iOS consumes packed wires; keep `make -C c ios-smoke` and the swift-parity job green; no redesign.
- Old formats may be retired without migration where that is the established practice (v5 replays, replay formats 5-8, envelopes without the roster trailer).
- Live games in the hosted DB must survive the deploy.

## 2. Target architecture

### 2.1 What exists today, in one paragraph

The kernel already does masking (`view.c state_put`), validation (`game_validate`, `fb7ebe9f`), the move pipeline (`wasm_apply_action`), the deal, the bot cycle (`wasm_bot_drive`) and event synthesis (`evwire.c`).
Around it, TS still builds a JS `Game` (`server/api/core/types.ts:106-160`) from JSONB columns and a hex blob (`utils.ts:559-722 loadCompleteGame`), marshals it byte by byte into the kernel (`engine.ts:399-478 marshalGame`, `src/wasm/clientGuards.ts:143-200`), re-reads kernel output by hand (`sdk/ts/wire/packed_read.ts:129-244`), resolves seats by `players.findIndex(p => p.player_id === userId)` in at least nine places, writes the JSONB public dual on every commit (`utils.ts:178-195 gameToPublicGame`, `commit_game` `jsonb_populate_record`), encodes the roster trailer and the response envelope in TS (`sdk/ts/wire/roster.ts:171-203`, `sdk/ts/wire/view.ts:165-192`), and on the web rebuilds `PersonalGame` objects that 30-odd components read field by field.

### 2.2 Invariants the target holds

1. A `games` row is exactly `state` (the kernel's durable blob) plus `roster` (the kernel's durable roster) plus scalars the kernel computed for SQL (`status`, `needs_bots`), plus host bookkeeping (`version`, `round_epoch`, `game_seed`, `logs_packed`, `bot_lease_*`, timestamps).
2. Every row has both blobs, including a WAITING lobby.
   "WAITING has no cards" is a kernel validation rule, so the five duplicated guards pinned by `e2e/waiting_stale_blob.test.ts` collapse into one C check plus one SQL rule.
3. A seat is resolved in C from the auth user id (`roster_seat_of`), never in TS.
4. Every per-viewer byte a client can receive (response envelope, `player_views.view`, `spectator_views.view`, realtime push) is written by C in one synchronous kernel section.
5. TS never reads a kernel slot across an `await`: every kernel section is load, operate, copy products out, all synchronous (the rule from `engine.ts` "Packed wire pipeline" and the resident-slot memory note).
6. `src/` can reach only the client-side generated modules (`view_layout.*.ts`, and `layout_hash.*.ts`, which holds nothing but the layout hash), never `game_layout.*.ts` and never a full-state reader (the S2 test).


The SQL no longer interprets a game: there is no `jsonb_populate_record` and no `status = 'waiting'` special case for `state`, because a WAITING blob with cards cannot be produced or loaded.
It keeps only bookkeeping rules: `game_seed` and `logs_packed` are cleared when `p_status` is WAITING, `round_epoch` is stamped on `p_closed_round`.

### 2.8 End of game (finalize)

`finalizeEndedGame` (`utils.ts:905-1019`) becomes: read `logs_packed` and `game_seed` (I/O), one kernel section that loads the table, encodes the v6 replay from seed and packed log (`kernelReplayEncodeV6FromGame` already takes packed bytes), encodes replay extras with names from the Roster and move times from the packed log (moving `moveTimesFromLogs` and `decodeLogs` into C), and computes the finish order and ELO deltas (`anim_finish_rows` plus a new `elo_deltas`).
TS then does the three writes (`game_snapshots` insert, `logs_packed` retire, rating upserts), reading player ids by seat through accessors.

## 3. Database migration design

### 3.1 Final `games` shape

Kept: `id`, `status game_status`, `state TEXT` (`\x`-hex, unchanged format v02), `game_seed`, `logs_packed`, `version`, `round_epoch`, `bot_lease_token`, `bot_lease_until`, `created_at`, `updated_at`.
Added: `roster TEXT NOT NULL` (`\x`-hex, `ROSTER_FORMAT_VERSION` 1, fixed 1227 bytes) and `needs_bots BOOLEAN NOT NULL DEFAULT FALSE`.
Dropped: `name`, `deck_length`, `discard_pile_length`, `flipped`, `players`, `power_suit`, `first_attacker`, `defender`, `table_battles`, `elimination_order`, `good_timestamp`, `good_players` (all `seed.sql:57-81`), plus the bridge-only `writer_gen` (3.4).
`state` becomes `NOT NULL` once every lobby has a blob.

Indexes: drop `idx_games_name` and `idx_games_playing_updated_at`; add `CREATE INDEX idx_games_bot_scan ON games(updated_at) WHERE needs_bots;`.

As built after the final pass (`20260918130000_table_bytea.sql`): `state`, `roster` and `logs_packed` are `BYTEA`, as are `player_views.view` and `spectator_views.view`; `game_snapshots.player_ids` is `UUID[]`; `game_seed` stays hex `TEXT`, which the kernel reads as text.
`player_hands`, `bot_hands`, `player_views`, `spectator_views`, `game_snapshots`, `chat_messages` keep their shapes.

### 3.2 The durable roster encoding (fixed width, versioned)

```
off   size       field
0     1          ROSTER_FORMAT_VERSION = 1
1     1          n seats (0..8)
2     1          title_len (0..200)
3     200        title bytes, zero padded
203   8 x 128    seat records (all 8 written; unused ones zero):
                   +0    1   id_len (0..36)
                   +1    36  id, zero padded
                   +37   1   name_len (0..64)
                   +38   64  name UTF-8, zero padded
                   +102  1   brain_len (0..23)
                   +103  23  brain key, zero padded ("" = human)
                   +126  2   reserved, zero
1227             end (the decoder refuses any other length)
```

Fixed width is chosen for three reasons.
It makes the one-time SQL conversion from JSONB a straight concatenation (3.4).
It lets SQL read a seat's id without a parser if it ever must (nothing in the target does).
It costs at most 2454 hex characters per row, about the size of today's `players` JSONB for a full table.

The brain is stored as the bot_roster key string, not a `STRAT_*` number, because the number is a build-time enum and a durable row must survive a rebuild; `table_load` resolves it with `bot_roster_find` and refuses an unknown key (Q11).

### 3.4 How live games survive the deploy: expand, switch, contract

Decision: **convert in SQL, do not add a C read path for the JSONB columns.**
A C read path would need either a JSON parser in the kernel (the owner deleted `json_out.c` and every JSON surface on purpose, `d6bce797`) or TS reading `players` JSON and writing a `Roster` through setters, which is TS knowing the game shape again.
The durable state blob needs no conversion at all: it stays v02 (Q2).
The conversion is one plpgsql function per blob, deleted in the contract step, with the precedent of `20260708130000_migrate_state_blobs_v2.sql`.

Why three deploys and not one: `deploy.yml:84-90` pushes the migration and then deploys functions, so a single migration that drops `players` breaks every running old function for the length of the function deploy, and an in-flight old request that loses a CAS race reloads JSONB that the new code no longer writes.

**4a Expand** (`server/impls/supabase/migrations/2026MMDD000000_table_expand.sql`, plus the same shape in `seed.sql`):

1. `ALTER TABLE games ADD COLUMN roster TEXT, ADD COLUMN needs_bots BOOLEAN NOT NULL DEFAULT FALSE, ADD COLUMN writer_gen SMALLINT NOT NULL DEFAULT 1;`
2. `legacy_roster_hex(p_players JSONB, p_title TEXT) RETURNS TEXT`: builds the 1227 bytes with `convert_to(..., 'UTF8')`, `lpad`/`rpad` on bytea via `decode(repeat('00', k), 'hex')`, and `bots.strategy_key` for `is_ai` seats; it RAISEs on an id over 36 bytes, a name over 64 bytes, a title over 200 bytes, or an `is_ai` seat whose bot row is missing, so a bad row fails the migration instead of loading as garbage.
3. `legacy_lobby_state_hex(p_players JSONB) RETURNS TEXT`: the v02 lobby blob, which has fixed offsets because every count is zero: `02 00` then status 0, n, power_suit 0, first_attacker 0, defender 0, discard `00 00`, has_flipped 0, flip `FE`, good mask `00000000`, has_ts 0, deck `0000`, battles 0, then per seat `{status (idle 0, ready 1), 0, 0}`, then eliminated 0.
4. Backfill in one statement: `roster = legacy_roster_hex(players, name)`, `needs_bots = status = 'playing' AND players @> '[{"is_ai":true,"status":"in"}]'`, and for every WAITING row `state = legacy_lobby_state_hex(players)`, which also repairs the damaged WAITING rows that still carry a finished session's blob (the case `loadCompleteGame` guards at `utils.ts:626-633`).
5. `CREATE OR REPLACE` the legacy `commit_game` and `create_game` (same signatures, so grants survive, and the lockdown loop runs anyway) so that they also maintain `roster`, `needs_bots`, and a lobby `state` from the JSON they receive, and so that they RAISE when `writer_gen = 2` (a row the new code already owns).
6. Create `commit_table` and `create_table` (they set `writer_gen = 2`), with the lockdown loop.
7. The partial index `idx_games_bot_scan`.

After 4a is deployed, old functions keep working and every row carries a valid `state` and `roster`.

**4b Switch** (edge functions only, no migration): every server reader and writer moves to `state` + `roster` and `commit_table` / `create_table`.
An old in-flight request that loses a CAS race against new code finds `writer_gen = 2` and fails that one request with a 400 instead of overwriting the roster from stale JSON.
The heartbeat reads `needs_bots`, which both generations maintain.

**4c Contract** (`2026MMDD000000_table_contract.sql`, and `seed.sql` rewritten to the final schema): drop the legacy columns, `writer_gen`, `commit_game`, `create_game`, both `legacy_*` functions and the old indexes; set `state` and `roster` `NOT NULL`; rewrite `delete_account`; apply the grants and policies of 3.3.
Deploy only after 4b's functions are live.

Proof before any of it ships: Phase 0.4 captures real rows written by today's code into a fixture, and Phase 4a's test applies the pre-migration schema, the fixture rows and the expand migration to a scratch database, then asserts that `table_load` accepts every row and that the envelopes C writes for every seat are byte-identical to the captured `player_views.view` and `spectator_views.view`.

#### Phase 3 as built (commits after `10384764`)

The C API is the one in 2.9 with these differences, each for the reason given.

- Every entry takes a `Table *` (a `Game *`, a `TableSnaps *`, the `Roster`, and the scope of the last operation) instead of `(Game *, Roster *)`.
  An operation's products depend on things neither struct holds: the hook snapshots it captured, the face-up trump before it (the DRAW-privacy rule), where its log records start, the acting seat, and whether it ended the game, dealt, changed the roster or is a lobby edit.
- `table_push(t, game_id, gid_len, viewer, out, cap)` takes the game id (the roster trailer names it) and no version (the version rides the realtime JSON `v`, not the bytes).
- `table_ready` and `table_add_bot` take the deal seed (`FOOLISH_SEED_LEN` bytes from the host's crypto); a deal saves and restores the deal RNG so its wide mode never leaks into the next table on the thread.
- `table_create` takes no title: C composes `<name>'s Game`, cutting the name on a scalar boundary when the title would pass 200 bytes.
- `table_reseat` takes the new order as `n x { u8 len, id }`; `table_retitle` keeps the web's rule (at most 50 UTF-16 code units before trimming, `String.trim` whitespace, not empty).
- New codes: `TABLE_E_WIRE (-108)`, `TABLE_E_CAP (-109)`, `TABLE_E_NOT_LOADED (-110)`, `TABLE_E_NOT_OVER (-111)`; `TABLE_MOOT` also answers a ready on a game already dealt, which today commits an unchanged row.
- A full table, a duplicate join, a bad title and a reseat that is not a permutation are `TABLE_E_ROSTER` with the `ROSTER_E_*` in `Table.detail`; a `table_leave` naming a bot is `TABLE_E_FORBIDDEN` (bots leave through `table_remove_bot`), and a reseat naming one player twice is refused (today's TS seats that player twice).
- `table_continue` clears the deterministic-deck flag, so every lobby blob carries flag 0, as the expand migration writes it.
- Strings and byte inputs cross into `wasm_table_*` back to back in the IO buffer with their lengths as arguments, not through generated `_str` setters: a name must reach C untrimmed and an empty or over-long id must reach C to be refused, which a NUL-terminated setter that throws on overflow cannot carry.
  Versions, epochs and clocks cross as doubles.
- as3 is the as2 sequence, one flags byte (`EVW_AS3_ROSTER`), then the roster trailer when that bit is set; a move's push is therefore as2 plus a zero byte.
- The board-seeded RNG hash moved from `wasm_api.c` to `game.c` (`game_state_seed`), the DRAW-privacy record writer to `view.c` (`log_record_put`), and the hand permutation check to `game.c` (`game_rearrange_hand`), so the wasm bridge and the table share one definition of each.
- `table_redact`, `table_rankings` and `elo_deltas` are in; `elo_deltas` computes `Math.round(10 * (s - E))` exactly for integer ratings from the ten rating differences at which a win gains a point.
- `sdk/ts/table/server_table.ts` creates a private bots.wasm instance by default (`createServerTable`) and wraps any exports object (`new ServerTable(ex)`); whether Phase 4b shares the edge's one instance is 4b's decision.

```sql
WHERE d.refobjid IN ('public.games'::regclass, 'public.player_views'::regclass, 'public.spectator_views'::regclass, 'public.game_snapshots'::regclass)
```

## 5. Risk register

### 5.1 Hidden information

- **Risk**: a C writer that emits a view for the wrong viewer, or a push that carries an unmasked step state.
  **Mitigation**: masking stays in `state_put` (unchanged); `table_commit_products` and `table_push` take the viewer from the roster seat, never from TS; S1 scans `player_views`, `spectator_views`, responses and `as3` pushes after every phase; `table_parity` asserts byte equality with today's masked outputs before cutover.
- **Risk**: the client-side module exposes a full-state reader.
  **Mitigation**: `TableView` has no deck and one hand by construction; S2 pins the import allowlist (Phase 5a).
- **Risk**: hosted's realtime channel policies differ from git.
  The policies on `realtime.messages` were never created by a migration before `20260917120000` (only `seed.sql` and a hand-applied hosted copy), and the fix branch found that `seed.sql`'s `gu-` policy refused every owner, yet live web play worked, so hosted likely carries a different `gu-` policy, possibly a looser one, or RLS on a different partition.
  **Mitigation**: before applying `20260917120000` and `20260917130000`, the owner runs these read-only queries on hosted and compares them with `seed.sql`; the migrations `DROP POLICY IF EXISTS` and recreate by name, so a hosted policy under another name would survive them and needs its own drop.
  ```sql
  SELECT policyname, permissive, roles, cmd, qual, with_check FROM pg_policies WHERE schemaname='realtime' AND tablename='messages';
  SELECT relname, relrowsecurity, relforcerowsecurity FROM pg_class WHERE relnamespace='realtime'::regnamespace AND relname LIKE 'messages%';
  ```
  Expected after both migrations: RLS enabled on `messages` and its partitions, and exactly the `seed.sql` set (the exact-topic `gu-` and `chat:` SELECT policies, `game-` for authenticated, and the service-role INSERT policies), with no `user-` policy and no client INSERT policy.
- **Risk**: `game_seed` leaks through a new path (it seeds `g_rng_base`, `wasm_api.c:268-279`).
  **Mitigation**: `game_seed` is never an input to any `table_*` product; it is passed only to `set_rng_base` and the replay encoder; S1 greps payloads for the 64-hex seed.

### 5.2 CAS and concurrency

- **Risk**: an edge isolate serves concurrent requests (`edge_runtime` per_worker locally), and a kernel slot read across an `await` gives one request another game's state.
  **Mitigation**: every kernel section is synchronous (2.2 invariant 5); the bot loop reloads after its one await (2.7); a test runs two interleaved `runTableOp` calls on different games in one module instance with an injected await between load and commit and asserts both commits are correct.
- **Risk**: the CAS fence changes meaning when `status` stops being column-authoritative.
  **Mitigation**: `commit_table` still fences on `version` only; `status` is written from the kernel on every commit, so the column and the blob cannot disagree after 4b; the fixture test covers rows written before.
- **Risk**: deploy rollover writes from old isolates.
  **Mitigation**: `writer_gen` (3.4).

### 5.3 Realtime payload shape

- **Risk**: an open web tab from before Phase 5a receives `as3` and ignores it.
  **Mitigation**: `AnimationContext.tsx:856-860` drops unknown `t` without error, and the same tab still receives `player_views` row pushes (`ServerContext.tsx:348`), so it keeps a correct board without animations until reload; Phase 5b waits for Phase 5a to be deployed.
- **Risk**: dropping `m` (message prose) hides text a user sees.
  **Mitigation**: nothing in `src/` renders `event.message` (checked: the only reads are `AnimationContext.tsx:837-842`, which set it); Q7.

### 5.4 iOS compatibility

- **Finding**: iOS does not only call C.
  `ios/FoolishNet/PackedGame.swift:61-107` parses the envelope header, `sdk/swift/MaskedView.swift` parses the `state_put` layout, and `ios/FoolishNet/EnvelopeRoster.swift:83-125` parses the roster trailer, all in Swift.
  So the envelope, the masked view layout and the trailer are frozen by shipped App Store builds.
  **Mitigation**: C writes all three byte for byte as today (Phase 2 and 3 parity tests); `npm run test:swift-parity` runs the real Swift decoders against C-written bytes; `VIEW_FORMAT_VERSION` 1 and `GAME_RESP_FORMAT` 1 are not bumped.
- **Risk**: the trailer's good-player ids and timestamp change (seat order instead of insertion order, `has_ts` 0).
  **Mitigation**: Swift decodes both fields and reads neither (no use of `goodPlayers` or `goodTimestamp` outside `EnvelopeRoster.swift`); the swift-parity test asserts decode success, not those values.
- **Risk**: iOS request bodies change.
  **Mitigation**: `meta` keeps its JSON body (`OnlineService.swift:37-85`), `action` keeps the awire envelope (`PackedAction.swift`), and the responses keep their formats.
- **Risk**: `Player` shrink breaks `c/ios/ios_api.c`.
  **Mitigation**: Swift never sees `Player` (`c/ios/include/ios_api.h` exposes no struct); `make -C c ios-smoke` and `ios-goldens` in Phase 3b.

### 5.5 Wasm artifacts: oracle.wasm and oracle-mt rebuilds

- **Risk**: `game.h` changes (Phase 3 lobby rule, Phase 3b `Player`) leave `public/oracle*.wasm.gz` stale, the failure `wasm.yml:11-13` describes.
  **Mitigation**: every phase that touches `c/src` rebuilds all five modules and re-stamps `WASM_STAMP`; `scripts/check_wasm_freshness.sh` gates it; the layout hash check (Phase 1) turns a stale oracle into a load-time error instead of a wrong answer.
- **Risk**: the local Homebrew toolchain produces bytes that differ from CI's (`check_wasm_freshness.sh:12-16`).
  **Mitigation**: unchanged practice: artifacts are built on the Mac and judged by stamp, not bytes.

### 5.6 Fixture churn

- **Risk**: 81 e2e files move, and a mechanical rewrite silently weakens a test (a fixture that no longer reaches the branch it was written for).
  **Mitigation**: fixtures go through `game_validate`, so an invalid fixture fails loudly; every rewritten file is mutation-checked on its main assertion; rewrites fan out in groups of about ten files with a coverage diff (`npm run coverage:e2e`) per group; deleted tests are listed in the commit message with what replaced each.

### 5.7 libclang skew

- **Risk**: CI's libclang 18 (ubuntu-24.04) spells typedef names differently from Homebrew LLVM 22.1.8, so `gen.sh --check` is red forever and gets switched off.
  **Mitigation**: pin LLVM 22 in the CI job (Q12); make the layout hash independent of spellings; generated identifiers come from declared names, which both versions report identically for the roots used (checked by running the Phase 1 test on both versions once).

### 5.8 Deploy ordering between migration and edge functions

- **Risk**: `deploy.yml` runs `db push` then `functions deploy`, so a destructive migration lands before the code that tolerates it.
  **Mitigation**: expand, switch, contract as three separate owner deploys (3.4), each safe with the previous code.
- **Risk**: the web (Vercel) and the edge functions (Supabase) deploy independently.
  **Mitigation**: Phase 5a accepts both push formats; Phase 5b switches the server; the `as2` branch is deleted only after a day.

### 5.9 Cold start and memory

- **Risk**: `create` and every lobby edit now instantiate bots.wasm (65 KB gz, 36 pages), where today a lobby edit pulls no kernel for `create`.
  **Mitigation**: measured gate (4.0); if create's cold start regresses more than 10 %, build the `table_*` entries into rules.wasm as well and load that module for `create` and `meta` (Q10 fallback).
- **Risk**: the `TableCommit` arena needs more IO buffer than `WASM_IO_CAP` (72 KiB, `wasm_api.c:57`).
  **Mitigation**: products are bounded (state under 300 B, roster 1227 B, nine envelopes under 1.5 KB each, logs of one bot cycle), pushes are written one viewer at a time into the IO buffer as today; `npm run test:mem` gates pages.

### 5.10 Durable data refusals

- **Risk**: stricter C loaders (roster refusal, lobby-cards rule, unknown brain) brick a live game that loads today.
  **Mitigation**: the 0.4 fixture includes every row shape the code can write, and the expand migration's backfill repairs the one known damaged shape; the owner can run the same conversion SQL read-only (`SELECT id FROM games WHERE legacy_roster_hex(players, name) IS NULL`, with the RAISEs turned into NULLs) before applying 4a.

## 6. Open questions and recommendations

**Q1. Should the kernel store the good-players insertion order and the good timestamp value (a v03 blob)?**
Recommendation: no, retire both.
Evidence: every consumer uses membership only.
The web reads `good_players.includes(me)` (`ActionButtons.tsx:154`, `KeyboardPlayMode.tsx:442`, `Tutorial.tsx:54`) and feeds the rest back into its own decoder (`AnimationContext.tsx:815-816`); `good_timestamp` is never rendered; iOS decodes both into `EnvelopeRoster` and reads neither; the server only carries them from row to envelope (`packed_action.ts:167-168`, `game_cache.ts:61-62`, `player_views.ts:62-63`).
The kernel's `good_players_mask` and `has_good_timestamp` already hold everything any decision uses, and the order survives in `logs_packed` as LOG_GOOD records if anything ever needs it.
This departs from the direction as given, so it is flagged: if the owner wants order kept anyway, it belongs in a v03 blob exactly as the direction describes, and Phase 3 grows by that codec branch.

**Q2. Bump the durable state blob to v03?**
Recommendation: no.
With Q1, nothing in `state_put` changes: a lobby is expressible in v02, and the roster is its own blob with its own version byte.
No bump means no dual read path and no conversion of dealt games at deploy.

**Q3. C read path for existing rows, or a conversion step?**
Recommendation: SQL conversion in the expand migration (3.4), because a C read path needs JSON in the kernel or the game shape in TS, and the v1 to v2 blob migration is the precedent.

**Q4. Roster encoding and storage.**
Recommendation: fixed-width 1227-byte v1 format (3.2), stored as `\x`-hex `TEXT` like `state`, ids up to 36 bytes of text (UUIDs, and the short ids e2e and the native server use), brain as the bot_roster key string.

**Q5. Where does the table title live?**
Recommendation: in the roster, with `games.name` dropped in 4c.
The title only reaches clients through the envelope trailer, and keeping it in the roster makes every envelope a pure function of `(state, roster, game id, version, viewer)`.

**Q6. Which is authoritative for `status`, the column or the blob?**
Recommendation: the blob; the column is written from the kernel's value on every commit and exists for SQL filters and `player_views.status`.
The current "column-authoritative" rule (`utils.ts:647-652`, `view.ts:235-237`) exists to survive writes that bypass the kernel, which Phase 0.1 and 4c make impossible.

**Q7. Keep the event message prose and the `r` / `m` push extras?**
Recommendation: delete both.
No UI renders `event.message`; `r` becomes the optional roster trailer inside `as3`; `m` has no reader.

**Q8. How does account deletion redact names?**
Recommendation: SQL returns the user's game ids, the edge function runs `table_redact` and a normal CAS commit per game, which also rewrites the names inside cached views (today they keep the real name).
Names inside `game_snapshots.extras` are a separate, pre-existing gap: record it as a follow-up, not part of this migration.

**Q9. Lobby authorization policy.**
Recommendation: every lobby edit requires the actor to be seated, except `join`.
Removing another human stays allowed for a seated player (it is a shipped web feature, `Lobby.tsx:440-444`), `add-bot` and `remove-bot` require a seated actor, and `rearrange-hand` only ever touches the actor's own seat.
This closes the "anyone who knows a game id can kick anyone" hole without removing the feature; Phase 0.2's tests make the change visible.

**Q10. Retire rules.wasm and guards.wasm?**
Recommendation: yes, bots.wasm everywhere (the "one big wasm" direction already in force).
The server stops loading the rules embed in Phase 4b, the web stops shipping it (today it ships unused through `bots.ts -> engine.ts -> rules_wasm.ts`) and stops loading guards in Phase 6b, and both are deleted in Phase 8.
Fallback if create's cold start fails its gate: compile the `table_*` entries into rules.wasm for `create` and `meta` only.

**Q11. Keep the independent TS parity oracles (`personalize_game`, `game_done`, frozen TS bots)?**
Recommendation: delete them in Phase 8.
They are independent only because they are a second implementation of the game shape in TS, which is what this migration removes; their coverage is replaced by C unit tests of `state_put` masking, S1, `table_parity` (which compares against them one last time before they go), and the existing C difftests.

**Q12. libclang version for CI.**
Recommendation: pin LLVM 22 from apt.llvm.org in the structgen CI job, matching the Mac, and make the hash spelling-independent.
Not recommended: generating in CI only, because the owner builds wasm on the Mac and the hash must be known at that build.

**Q13. iOS Swift decoders that know byte layouts.**
Recommendation: out of scope, recorded as the follow-up it is: expose `client_adopt_envelope` through `c/ios/ios_api.c` as `fio_envelope_decode` and delete `PackedGame.swift`'s header parse, `MaskedView.swift` and `EnvelopeRoster.swift` in a later iOS release.
Nothing in this plan blocks it, and the parity tests keep the Swift readers honest until then.

**Q14. How long to keep `as2` decoding on the web?**
Recommendation: one day after Phase 5b is deployed, then delete, following the envelope-trailer precedent (`view.ts:130-146`).
As built: Phase 5b left the `as2` branch in `AnimationContext.tsx`; the owner's follow-up deletes it (with the `m.r` read) one day after 5b's functions are live.

**Q15. `offlinefun/localtest` TS harnesses.**
Recommendation: delete the ones that construct a `Game` in Phase 8.
They are research drivers superseded by the C CLIs, several depend on APIs Phase 4b removes, and porting them to fixtures would keep a TS game model alive for tools nobody ships.
Flagged because it deletes research code: if one is still in use, it gets a C CLI equivalent first.

**Q16. An unknown bot brain key in a stored roster.**
Recommendation: `table_load` refuses (`TABLE_E_UNKNOWN_BRAIN`) and the error is logged with the game id.
A brain removed from the wasm must be migrated off live rows in the same change, as `20260711130000_drop_non_wasm_bots.sql` did; silently playing `random` is the bug the A1 roster cutover found.

**Q17. Stale-round guard and action request/response codecs: TS or C?**
Recommendation: C (`table_act`, `table_request_decode`, `table_action_response`).
They are rules and byte layouts; TS keeps passing `round_epoch` from the row.

**Q18. Should the durable blob or the roster carry `Game.rules` (podkidnoy) for online games?**
Recommendation: no, not in this migration.
Online play is classic only today and `state_put` never carried the byte; adding a variant to online play is a product change with its own codec bump.

## 7. Next phases (owner-approved 2026-09-17, after the Phase 8 cleanup)

### Phase 9: the web takes its animation timing and ordering from the kernel

Owner: "keep the kernel as is [import-free] but let React use the timing and ordering it provides instead of whatever we do right now".

React keeps only rendering: the DOM, CSS transitions, the frame loop, screen coordinates.
The kernel provides what happens, in what order, with what durations, and the board at each step.

Starting point already in C (`c/src/anim_plan.h`): plan building with `duration_ms` and `start_ms` per step, the count-freeze and the veil, the timing policy (`ANIM_TIME_MS`, `anim_step_duration_ms`), the optimistic policy (`anim_should_drop_stale`, `anim_stale_optimistic_on_table`, the revert/keep/clear decision, the dedup key), the conflict model, and the beats model lifted from iMessage (`AnimBeat`, `AnimBeats`, `AnimSurfacePlan`).
`sdk/ts/gen/anim.bots.ts` already generates readers for `AnimPlan`, `AnimPlanStep`, `AnimBeat`, `AnimBeats`, `AnimCounts`.

Steps:

1. Audit, written down before any change: what `anim_plan.h` covers versus what `src/contexts/AnimationContext.tsx` decides today.
   Specifically: optimistic TIMING (when a predicted flight starts, its duration, how a confirming push replaces it mid-flight) as opposed to optimistic policy; the refusal return flight; the resync path; the rematch reset; and hand ORDER (`mergeReplayHandOrder` in `ReplayScreen.tsx`, which is the divergence the iMessage work found).
2. Add the gaps to C, and re-export the plan and beats builders (`wasm_anim_build_plan` was deleted as dead code when the web's bridge went).
   The web needs a RE-ASKABLE call, not just a plan up front: a pull per frame (`client_anim_advance(now_ms)` returning the current step plus the next deadline) so a push landing mid-flight is answered by the next call instead of by cancelling a timer chain.
   No new wasm imports: the host supplies the clock as an argument, the kernel stays import-free.
3. React switches to generated snapshots of the plan and beats, deleting the serial `setTimeout` queue (its own TODO calls it an anti-pattern), the `ANIMATION_TIME = 500` constant, every `type === 'attack_pass' | 'cover' | 'pickup'` branch, and `optimisticPassState` (the kernel's dedup key and optimistic policy answer what it guesses).
