Foolish Architecture

A Durak card game that is secretly one C kernel wearing five costumes: a web app, a Supabase backend, an iPhone app, a serverless iMessage game, and a replay format that fits a whole match in a QR code. This document maps every subsystem and the byte-level contracts that hold them together.

§1 · доктрина / the one idea

One kernel, four layers

The whole system hangs off a single principle applied without compromise: the domain logic has exactly one implementation, in a portable compiled language, and it runs unchanged in every environment.

The game rules live once, in C (c/src/game.c + legal.c + view.c + replay.c). That C compiles to WebAssembly for the browser, the Deno edge functions, and Node tests — and to a native static library for iPhone. There is no TypeScript copy of the rules "for the client" and no separate server implementation; the TS and Swift that remain are thin marshaling bridges. WASM is what makes the shared core real instead of aspirational: most "isomorphic" code sharing degrades into two implementations that drift, but a compiled kernel guarded by byte-level parity tests cannot drift, because there is only one set of bytes.

Everything decomposes into four layers (docs/ARCHITECTURE_AS_A_PATTERN.md):

LayerWhat it isWhere it lives
Corepure reduce(state, command) → events, validation, legalitygame.c / legal.c — compiled once, runs everywhere
Contractpacked byte formats for state, commands, events, viewsawire / evwire / view / logwire / msg_wire / replay codec (§5)
Projectionsproject(state, viewer) → bytes — the only serializer; redaction lives hereview.c — "you only see your own hand" is a C function, not a TS filter
ShellHTTP, DB, sockets, auth, rendering — all impure, all deliberately dumbedge functions, React components, SwiftUI views

Before the TypeScript engine was deleted, a differential harness replayed ~100,000 mirrored actions plus ~30,000 adversarial probes through both engines with identical seeds and byte-compared states, logs, events and rejection messages: zero divergence. The retired TS lives on, frozen verbatim, as the oracle in an ongoing parity lattice (§12). In textbook terms this is event-sourced + CQRS + functional-core — with the novel last mile that the write model is a portable compiled artifact, so the same validator runs on the client and buys optimistic UI and offline play for free from the same machine code.

§2 · карта / network topology

Three tracks, one kernel

Games flow over three transport tracks that never share state: a Supabase-backed authoritative-server track, a fully serverless iMessage track where the message is the game, and a local track where the opponent lives on your own device. Every box on the map runs the same C kernel.

Apple platforms web client backend / delivery bots the C kernel
  • Supabase track — web today, iOS written and awaiting its first end-to-end staging run, watchOS specced. Authoritative state in Postgres, moves as packed bytes, fan-out over Realtime (§6).
  • Serverless track — the iMessage extension. Every bubble carries the entire game; each device independently re-validates the whole history by replaying it through the kernel (§11). Live on the App Store as its own product.
  • Local track — offline play against on-device bots on iOS (the full ladder up to octogen, driven natively through one kernel call per cycle). In the browser the same consolidated module powers replays, the tutorial, and the Oracle rather than a shipped offline mode.
§3 · ядро / the c kernel

cnitro — the engine that is the game

The kernel under c/ (codename cnitro, ~45k lines) began as a bot research lab and became the production rules engine. Every live move on the server, every button gate in the browser, every iMessage bubble, and every replay runs its machine code.

ModuleResponsibility
game.c / game.hThe engine: deal, defender rotation, draws, eliminations, the log stream. Two independent thread-local LCGs (game + strategy RNG, same recurrence as the retired TS) so arena threads never race. Fires engine_snap_hook at exactly the points the old TS handlers cloned state for animation snapshots.
legal.ccalculate_legal_moves — legality and enumeration, preserving the TS emission ordering so "first matching" stays deterministic everywhere.
view.cPer-viewer projection (state_put) with hand masking — the only serializer, so redaction cannot be forgotten (§5).
replay.c / replay_steps.cThe rANS whole-game codec (2,040 lines) and the two-pass code→playable-game reconstruction that lets any client replay a shared code through the real engine (§8).
awire.c / evwire.c / logwirePacked wire codecs: actions in, per-viewer animation-event streams out, session log records (§5).
msg_wire.cThe FMSG iMessage envelope — the serverless track's entire protocol (§11).
anim_plan.cThe animation policy core — stale-broadcast dropping, optimistic reconciliation, flight planning — ported from the web client so a phone and a browser can never disagree about what animates (§9).
deal_rng.cChaCha20 (RFC 8439) for the reproducible 32-byte-seeded deal; integer-only, so identical on x86, arm64 and wasm32.
bot_roster.c / bot_drive.c / bot_knobs.cThe one table mapping bot key → brain → tuning knobs, the drive cycle (fair pick, silent-action bundling, stop conditions), and the pacing table (3000 ms with humans watching, 300 ms bots-only) — shared by server, phone and browser (§7).
*_strategy.c / cordite_sim.c / leafbook24 bot brains from random to octogen, the ~200-byte bitboard rollout engine, the exact endgame solver and its precomputed leaf book (§7).

Deck rules are settled constants: 2–5 players play 36 cards, 6+ play 52, hardcoded in card.h. Time and randomness are injected — the kernel never reads a clock, and determinism is load-bearing: it is what makes replays exact, the iMessage chain re-validatable, and the parity harnesses meaningful. The native build (make all) also produces the research fleet: cnitro_eval, cnitro_elo (mixed-pool Elo arena), cnitro_replay, cnitro_showcase (scores all-cordite games for drama), plus training-data generators for the distillation and value-net research tracks.

§4 · артефакты / wasm artifacts

One source, tailored artifacts — currently one big module

The kernel ships as WebAssembly for every non-Apple host. The build system can specialize per call site, but while the kernel surface is under heavy development the deployed shape is deliberately consolidated: one big module with everything in it does the real work everywhere.

Current state. bots.wasm — rules, views, all wire codecs, the replay codec, and every shipped bot brain in one 158 KB module (66 KB gzipped) — "adopts the engine slot" on load and serves the entire kernel API on a single instance, in the browser, on the Deno edge, and in Node tests. The client runs the whole kernel now, not a rules subset. The smaller specialized builds still exist around it (the 6 KB validate-only guards module that gates the UI synchronously, the rules-only embed, the spendthrift Oracle build), and per-call-site specialization remains the documented target shape once the surface stabilizes.

Shipping mechanics

  • The big module ships as a real binary asset (bots.wasm.gz), not a base64 embed — a static file on the edge, a fetched asset in the browser, with three runtime "doors" in sdk/ts/wasm/wasm_asset.ts. A base64 twin briefly existed and was deleted: two carriers of the same bytes is exactly how an embed once went stale for weeks while tests passed against the wrong kernel.
  • The small modules are gzip+base64 TS embeds generated by c/wasm/embed.mjs — one single-line literal (V8 folds chunked + concatenation into ~300 MB of transient garbage, which once killed edge workers during import), exported as a take-once function so the decoded string isn't pinned for the isolate's lifetime.
  • Build flags are doctrine: -Oz cuts every module ~40% for zero warm-perf cost; LTO is banned (wasm-ld LTO silently corrupts the indirect-function table — caught by the fuzz suite); -ffast-math is banned (floats must stay IEEE-identical to the TS oracles); explicit export allow-lists replaced --export-all so the linker can dead-code-eliminate; a post-link wasm-opt pass recovers cross-object inlining for −6.4% size. A clean rebuild reproduces the committed binary md5-identically — a byte delta means your change, not the compiler.

Memory as a build-time invariant

Every static buffer is sized from a measured maximum (~63,000 instrumented games), capped at ~1.4–2× the observed worst case, and — on the pinned modules — enforced by --initial-memory == --max-memory, so a buffer over budget fails the link, not production. Overflow always degrades cleanly (a bounds-checked error, a dropped animation frame, a loud --stack-first trap), never corrupts.

ModuleBeforeNowHow
guards.wasm256 KiB64 KiB — 1 page, pinnedvalidate-only compile; the page is L1d-sized on Graviton
rules.wasm3.31 MiB192 KiB — 3 pages, pinnedarena overlay aliasing replay scratch over action scratch (provably never live together), stack 64→32 KiB after a canary measured 14.3 KiB worst-case
bots.wasm5.13 MiB~1.37 MiB peakstack 256→64 KiB, streaming chooser, replay↔solver overlay, io overlay; grows once when the solver's 32 KiB TT warms

The security pass over the same boundary (docs/SECURITY_WASM_BOUNDARY.md) hardened the marshaling surface as defense-in-depth: every count clamped, every card sanitized, subset enumerators bounded (a hostile hand could previously wedge a request in ~2n recursion), verified by a fuzz gate of ~1,500 wild games plus ~14,000 malformed-game bot decisions — at zero measurable cost. A stale third copy of the wasm bridges under supabase/functions/_shared/wasm/ is vestigial: nothing imports it; the live modules live in sdk/ts/wasm/.

§5 · протокол / the contract layer

The wire — six packed formats

Game state is a C buffer end to end. JavaScript and Swift objects exist only at the render boundary and the DB edge; everything in between is kernel-produced packed bytes, little-endian, with a card as one byte (suit·13 + value−1, 0xFE hidden, 0xFF none).

FormatDirectionWhat it carries
awire v1client → serverA move: [kind][n][cards…][covers…]. The bytes guards.wasm validated are the exact bytes the server kernel applies — one decoder compiled into both. Request envelope v2 adds intent_version (u32) for the stale-round guard; the response is 7 bytes: [fmt][APPLIED|REJECTED|MOOT][reject_code][version]. Kernel reject codes occupy 0–21; server-edge codes live above (REJECT_STALE_ROUND = 100) so a client can tell rules from policy by the code alone.
view v1server → clientThe per-viewer masked state, produced only by view.c: deck and other hands as 0xFE with counts preserved, other seats' intent flags zeroed, battles public. One envelope ([magic][flags][seat][version][roster JSON][masked state]) serves the create response, the player_views cache rows, and the spectator rows alike.
evwire v1server → clientThe animation-event stream, personalized in C per recipient: per event a type / seat / message code / from→to locations / cards (deal & refill identities masked unless yours) — and its own masked snapshot, so the client materializes state per step and never reconstructs it. This one stream drives live play, replays, the tutorial, and iMessage bubbles.
logwire v1persistenceHeaderless session-log records, deliberately concatenable so commit_game appends by plain hex string concat under the version fence — exactly-once by construction. Draw identities are masked before the bytes reach the DB, so the stored stream is safe to feed bot beliefs: the no-cheating contract, structurally.
replay v6share codesA finished game as one rANS-coded integer (§8).
FMSG v1iMessageThe whole game in a message URL (§11).

The masking rule is worth stating as policy: the server never materializes an unmasked object on the hot path. Hidden data leaves the kernel already redacted, and the DB side matches — row-level security cannot hide a column, so a migration replaced the games-table RLS policy with column-level SELECT grants that simply omit state, game_seed and logs_packed. The masked path is the only path.

§6 · сервер / the supabase track

Five edge functions, one CAS, no locks

The backend is a stateless shell around the kernel: five Deno edge functions, a Postgres schema built around a ~96-byte state blob, optimistic concurrency instead of locks, and Realtime fan-out of pre-masked byte streams.

The deployable lives in server/impls/supabase/; platform-agnostic game logic sits above it in server/api/ (no Deno, no HTTP), and a proof-of-concept native C server (server/impls/native/) demonstrates the API is host-agnostic. A machine-checked layering test enforces the one-way DAG core → sdk → common → adapter — the adapter is swappable because nothing below it may know the vendor exists.

FunctionContract
actionAll five moves plus the bot nudge, dispatching on body type — with a binary fast path for application/octet-stream packed actions. Replaced six per-move functions.
metaLobby verbs: start / join / exit / continue / add-bot / rearrange / rename. One line of real code around handleMetaAction.
createReturns the creator's packed view envelope before persisting — the DB write rides EdgeRuntime.waitUntil with retries, taking a ~594 ms cold round-trip off perceived latency.
bot-heartbeatTwo modes on one URL: SCAN (from pg_cron) and DRIVE (per game). §7.
delete-accountApp Store / Play data-deletion compliance: auth → PII-scrub RPC → auth-user delete.

Persistence

  • The blob is authoritative. Once dealt, games.state (~96 bytes hex) is the game; the JSONB hand tables stop being written and persist only for lobbies. game_seed (32-byte ChaCha seed) and logs_packed are server-only columns hidden by grants.
  • commit_game is one 14-parameter RPC committing blob, view caches, spectator view, log append and round-epoch stamp in a single version-fenced transaction. Callers retry conflicts up to 5 times. A per-isolate LRU cache (256 games), fenced by the same version, removes one of the two DB round-trips per move — "a stale entry costs one conflict and a reload, never a wrong write."
  • The stale-round guard: a move carries the version its author saw (intent_version); if that predates round_epoch — the version at which the current round began — the move targeted a battle that no longer exists and is rejected as stale rather than re-validated into the fresh round (the "revert, then it plays anyway" ghost). Round-scoped, not version-scoped, so legitimate cross-version throw-ins still flow.
  • Identity is deliberately minimal: username → SHA-256 → 16 hex chars → @foolish.cards pseudo-email, guest-first, mirrored byte-for-byte on iOS. Edge auth verifies JWTs locally against the project JWKS (asymmetric algorithms only — the alg-confusion defense) to keep supabase-js out of the cold-start boot graph. Personal identity never enters the kernel blob; the caller's auth id is the player id, and a seat is just its array index.

Realtime holds no websocket on the server: one REST POST fans out every recipient's envelope — per-player channels for masked streams, a public spectator channel, Postgres-changes on the player_views cache (RLS-enforced per row) for state, and a chat channel. Bots are skipped; they have no clients.

§7 · боты / bots

The ladder, the loop, and the no-cheating contract

Bots are real players: rows in the DB with a strategy key, the same wire, the same CAS. Every algorithmic brain is C, and the strongest ones are belief-constrained determinized Monte-Carlo players under a strict contract — no LLM, no neural net, no reading hidden state. The bot sees exactly what an attentive human sees, and derives the rest.

The ladder

c/src/bot_roster.c is the single table mapping key → brain → knobs → seeded/offline flags — consumed by the server, the phone and the browser, and parity-policed so "the phone and the site run different bots" cannot recur (it did once: iOS ran cordite at the arena budget). The player-facing ladder renders strength as air distance to the Kremlin:

RungKeyBrain
MiamirandomUniform over the legal-move list.
New YorkhandwrittenLowest-first heuristic, an exact mirror of the retired TS bot.
SeoulrobustaThe first Monte-Carlo bot — public-info sampling.
MadridfirecrackerRobusta's MC with a smarter rollout policy.
ViennablackpowderBelief-constrained determinized MC + exact 2-player endgame solver.
St. PetersburgcorditeBlackpowder's successor: bitboard rollouts, common random numbers, loss-avoiding root solver, rank-floor inference.
MoscowoctogenThe shipped apex — cordite's line with an extended exact-solve window; provably never worse than its predecessor.

How the strong ones think, in one paragraph: rebuild a belief from the public log every call (cards publicly picked up and not yet replayed are pinned to their holder; the flipped trump's taker is known by rule; a defender who picked up with one attack uncovered demonstrably had no cover — applied to 3 of 4 sampled worlds as a mixture, so a bluffing human misleads most worlds but never all); sample determinized worlds consistent with that belief; evaluate every candidate move on the same worlds with the same RNG stream (a paired test — world-luck cancels); and once the deck is empty heads-up, stop sampling and solve: the unseen pool is the opponent's hand by pure deduction, and an exact alpha-beta with a 32 KiB packed transposition table plus a ~27 KiB precomputed leaf book plays the endgame perfectly. The C rewrite made each decision roughly 15× faster than the TS original — banked as latency, not strength, because budget sweeps showed the deployed search already sits at its saturation knee (2×/4× worlds moved win rate 40.0% → 40.0% → 39.0%).

§8 · повтор / the replay codec

A whole game in a QR code

A finished game is entropy-coded into a single integer and base32'd into a URL short enough for QR alphanumeric mode. The trick: derived events cost zero bits, because the decoder doesn't parse a recording — it re-plays the game through the engine and only pays for the genuinely random bits.

  • Format 6 knows everything. The v5 line deferred hidden-card identities and reconstructed them by retrodiction plus a complement backfill once the fool was known — exact at game end, a guess mid-game, and the guess once made the Oracle judge a provably forced move as a mistake. v6 entropy-codes each hidden card inline at the moment it's dealt or drawn, uniform over the still-unseen pool; with dead "goods" trimmed, a 1,024-record log covers all but 0.05% of 8-player games, measured over 139,515.
  • Playback is a VHS deck (ReplayScreen.tsx): the real game board fed by the decoded frames, with a scrubber, bout skips, a speed dial whose 1× honors recorded timing (a three-day sulk between moves really takes three days, countdown on screen), a reveal-eye that shows every seat's exact hand (the code is replayed once per seat and each seat's own frames are read — exact by construction), and a telestrator pen for commentary. Stepping backward inverts flights for presentation only; the committed board is always the kernel's.
  • The tutorial is a replay: a frozen code of a real engine-played game (seed 211 of 1,500 searched, scored so the learner personally performs every taught move) with narration on top — the fourth consumer of the same pipeline after live play, replays, and iMessage bubbles.
  • An optional extras blob packs player names and per-move timing spanning nanoseconds to weeks; bots carry a reserved name prefix so bot-vs-human survives the name-only codec. /history decodes every finished game from its snapshot row — re-watchable forever.
§9 · клиент / the web client

A thin shell that computes its own pixels

The Next.js client (React 19, App Router) owns rendering, optimism and atmosphere — and almost nothing else. It gates every button through the kernel, reconciles broadcasts through logic that now lives in C, and ships zero texture files: every surface is computed in the browser and cached in IndexedDB.

  • KernelGate: the provider tree awaits the wasm kernel before rendering anything — realtime decode is synchronous, so "probably warm" isn't good enough. One GameBoard composition serves four state sources: live play, replays, the tutorial, and the iMessage /m/ page, each supplying a different implementation of the same read surface.
  • Optimism with three verdicts: a tapped card flies immediately; when the authoritative broadcast arrives, each pending card resolves to revert (never accepted — fly it home), merge (accepted, its own broadcast still in flight — keep it injected), or clear (accepted and already swept off by this broadcast's own pickup — drop silently, the incoming events animate it). Out-of-order broadcasts drop by version; reconnects re-apply unconfirmed cards over the REST resync. All three decisions now delegate to anim_plan.c through the wasm bridge, with the original TS preserved verbatim as a parity oracle — a phone and a browser disagreeing here would fork the feed.
  • Kernel-gated input: guards.wasm instantiates once behind the load screen (~1 ms), after which every affordance — buttons, drag targets, keyboard play, one-tap cover — is a synchronous wasm call. Opponents marshal as placeholder cards; provably safe because no validator inspects another player's card identities, only counts. There is also a complete second input path: arrow-key navigation with a cursor, built entirely on the shared read surface and the data-* attributes the board already exposes.
  • Procedural atmosphere: a Barnsley-fern IFS fractal card back (a million iterations, CPU compute → WebGL points → PNG blob, 2D-canvas fallback), woven-wool background, parametric wood grain, seeded concrete — each cached three deep (module blob URL → in-flight promise → IndexedDB, with a deadline race because iOS Safari can hang indexedDB.open() forever). Selecting Russian flips the whole app to a sharp-edged Soviet theme — square corners, hard shadows, a red-and-gold SVG card back, hand-drawn flag icons — driven by language, through CSS attribute selectors, a programmatic style context, and a parallel icon set. Localization is a ~348-key union type in en/ru/ko, so a missing translation is a compile error.
  • Routes: / auth, /dashboard, /:game_id — which doubles as the replay route (a path segment longer than any game id is a replay code), /leaderboard (humans and bots on one Elo ladder), /history, /tutorial, /m/[payload] (§11), plus policy pages. A parked PWA/service-worker layer sits in offlinefun/, excluded from the build; its live half is the headless bot-arena harness and the frozen TS strategy oracles.
§10 · оракул / the infinite oracle

Unbounded analysis in a browser tab

Pause a replay on a decision, press the crystal ball, and octogen — the strongest shipped bot — deliberates in your browser over that exact position, scoring the played move and every alternative as error bars visibly shrink.

The design inverts the server's economics: the shipped modules were squeezed byte-by-byte because a server handles many games; the replay page is one user, one position, hundreds of megabytes and minutes of attention. So oracle.wasm spends freely — an 8 MiB transposition table (a strength knob, 256× the server's), a full-size stack, and a fleet of up to 8 web workers, each with its own instance, streaming Monte-Carlo batches into a Welford accumulator until standard error converges (n > 65,536 and SE < 0.005, hard cap 180 s). The shipped modules stay byte-for-byte untouched.

Two honesty rules are load-bearing. The Oracle reasons from the acting seat's view — a v6 replay knows every hidden card, but draw identities are re-masked before they reach the bot, because handing it the truth "would not be a better analysis, it would be a different game — one where the bot cheats." And its verdicts stay humble where the math does: chess.com-style move classes (best → blunder) ride adjusted deltas, exact-solver verdicts are labeled as such, and the one thing it cannot do — cyclic deck-empty endgames whose game graph loops through pickups — is documented as the boundary of the whole approach (retrograde analysis over ~37M positions solves them offline; a browser tab does not). The UI is a vintage car-stereo equalizer faceplate: amber segment displays, a memory toggle, EQ bargraphs for convergence. It is also the seed of a chess.com-style paid Game Review tier — with the stated tension that a client-side oracle is not server-meterable, so the web paywall must meter the service via issued tokens, not the bits.

§11 · яблоко / apple platforms

Native kernel, serverless messages

On Apple platforms the kernel drops the wasm costume: the same C sources build into Foolish.xcframework, linked statically by a shared FoolishKit framework. Two products ride it — a full iOS app (Supabase track + offline bots, not yet submitted) and the Foolish Messages iMessage app, live on the App Store at 1.0, build 21.

The serverless track — the message is the game

  • No identity, by construction. There are no accounts and Apple's participant UUIDs are per-device-per-conversation, so the only on-wire identity is a self-reported nickname. A device resolves "which seat am I" from an App Group cache written at claim time, then sender inference, and otherwise renders the public spectator board — never a guess. The extension is provably networkless: a lint script fails the build if it ever links a network stack.
  • Lobbies and races are kernel problems. Every chat shape routes through a WAITING lobby (the "DM deals immediately" shortcut was deleted as a deck-reroll hole); racing sends resolve by Rule P in msg_wire.c — at equal round and turn, more joins wins. Fair-tempo rules (a 15-second pickup hold via a wire-carried clock; a stall-breaker any impatient device can invoke through the ordinary public API) need no protocol extensions.
  • The first rules variant lives here: podkidnoy (throw-in only, no pass) vs the default perevodnoy (transfer). One kernel bit whose zero is the classic game, read by the engine, the enumerator and the rollout sim — the UI needed no gate at all because every affordance already comes from the kernel's own menu. The replay codec pins the mode as a probability-model bit; the FMSG header respends its reserved byte as a rules byte; the lobby renders it as a wooden checkbox where whoever changes the rule cannot start the game.
  • The web handoff: macOS Messages runs no iOS extensions and Android sees a raw URL, so the link is a page — /m/<payload> decodes by replaying the chain and renders the kernel's spectator view (masking is view.c's decision, not the page's), with a server-rendered unfurl so a Slack or Messages preview can title the game without running JS. Finished bubbles funnel to a replay link and the App Store.
  • The rest of the fleet: the host app implements the full Supabase track byte-for-byte (packed actions with intent_version, view-cache subscriptions) and offline play against the entire on-device ladder — one kernel call per bot cycle, pacing included; procedural textures are ported but baked at build time (an extension's memory ceiling made runtime generation a crash suspect). watchOS is a designed-and-parked scaffold. A never-shipped harness app mounts the real extension UI with a fake 8-participant transcript, because Apple's simulator can't.
§12 · паритет / testing

The parity lattice

The architecture's enabling discipline: wherever two implementations of one truth exist, a mechanical gate proves they agree — and wherever a second carrier of the same bytes existed, it was deleted rather than gated.

  • The e2e suite runs the deployed code. ~80 files drive the real _shared handlers, the verbatim commit_game and lease plpgsql, and the exact client reconciliation modules the React contexts import, against a real Postgres — only PostgREST and Realtime are shimmed by a ~180-line pg adapter. The fuzz and rearrange suites have found and fixed real card-duplication exploits; the seven documented client races run in both delivery orders with pinned deals.
  • Byte-level parity gates: packed-wire parity proves the C pipeline's state blobs, logs and per-recipient event streams byte-identical to the legacy JS path (and asserts on the raw bytes that no viewer's stream ever carries another hand); the state codec round-trips 36,787 seeded states losslessly; guards.wasm must return the exact verdict of the server kernel; bot parity replays the frozen TS strategy oracles move-for-move against the kernel with pinned RNG streams; roster parity keeps the three copies of the bot table in agreement; iMessage fixtures are sealed by the native kernel and decoded by the wasm one.
  • Native difftests mirror the critical ones inside C itself: bitboard sim vs struct engine, bitboard solver vs struct solver, replay round trips, the FMSG tamper matrix, and the animation core's C twins of the React animation-quality tests.
  • Regression suites for production war stories: a memory suite guards the two "Memory limit exceeded" outages (the base64-concat parse blowup; solver-scratch growth) and asserts kernel memory is exactly flat once warm; a layering test machine-checks the four-tier dependency DAG; kernel coverage floors (90% line / 74% branch over the core) and server/client coverage gates run in CI.
§13 · дисциплина / the playbook

The performance discipline, in five moves

Nearly every optimization in the system is an instance of one rule: prove what this exact deployment doesn't need, collapse the program to fit, and enforce the collapse at build time.

MoveAnchor in this repo
1 · Optimize the binding constraint onlyPerceived latency is the 500 ms card flight, not compute; the server residue is DB round trips; cordite's strength curve sits at its saturation knee, so the 15× speedup was banked as latency.
2 · Turn limits into build-time invariantsPinned linear memory makes an over-budget buffer fail the link; static asserts guard arena overlays; caps overflow into clean errors, never corruption.
3 · Specialize the artifactTailored modules per call site from one source; export allow-lists enable dead-code elimination; hot files at -O3, cold code built for size — cold edge workers never tier past the baseline compiler anyway. (The current consolidated module is a deliberate, temporary inversion of this move while the kernel surface grows.)
4 · Fit data to the machine and the boundaryguards pinned to one L1-sized page; the solver TT packed 16→8 bytes, 2-way, one cache line per bucket — 1 MiB → 32 KiB as a strength-neutral ladder; a card crosses every boundary as 1 byte.
5 · Exploit liveness and stabilityNever-concurrent buffers alias the same address; state stays resident across a bot's choose→apply; a version-fenced cache skips the DB load; replay's derived events cost zero bits; the leaf book terminates solved subtrees outright.

And the process beneath the tactics: every optimization measured before and after with a real harness; every one reversible via a knob; every one gated by correctness tests (the fuzz suite is why aggression was safe); and after each win the budget is re-pinned lower, so the ratchet only turns one way.
