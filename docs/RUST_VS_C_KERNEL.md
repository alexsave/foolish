# Should the kernel be written in Rust?

An examination of the C kernel (`c/`), its WASM/iOS/server deployments, and
the native C server, with a Rust rewrite in mind. Treated as greenfield: zero
daily users, so migration cost is at its lifetime minimum. Includes empirical
POC benchmarks (`rustpoc/`) where three real kernel hot paths were ported to
Rust and measured against the shipped C.

**TL;DR — recommendation in one paragraph.** Performance is close to a wash
and should not drive the decision: POC ports of four real hot paths — now
including octogen's dominant cost, the exact endgame solver — land at
legal movegen +14%/+4%, MC playouts −2% vs gcc / +13% vs clang, wire parsing
−5%, and the solver +5.5–9% (the one honest regression, on a
budget-capped-per-decision component), with every port verified bit-identical
down to the solver's 46.9M-node search tree; the kernel is ~2 orders of
magnitude below the plumbing in end-to-end cost anyway. The decision axis is
*correctness class*: this repo has a documented ledger of ten shipped
memory-safety bugs (six in the server, all six compile-time-preventable in
safe Rust; two in the kernel found only by fuzzing) plus four **live**
residuals of the same classes, and it pays an ongoing tax in
fuzz/ASan/Helgrind machinery and hand-audited invariants that Rust's type
system would subsume. Recommended: **rewrite in phases, server first, rules
core second, bots last** — the differential harnesses already in the tree
make a bit-exact migration verifiable (proven: the POC playout port is
bit-identical to the `-ffast-math` C build). The two places where C is
genuinely better today — the 6.5 KB `guards.wasm` size discipline and the
solver's validation-ladder-frozen behavior — are the two things to port last
or not at all.

---

## 1. What "the kernel" is

- `c/src` — 28.6 KLOC: rules engine (`game.c` 1,075 + `legal.c` 523), wire
  codecs (`msg_wire.c`, `awire.c`, `evwire.c`, `view.c`), the v2–v6 replay
  codec (`replay.c` 1,882 — rANS entropy coder, **frozen wire format**), and
  ~9.6 KLOC of shipped bot ladder (`cordite_sim.c` 2,369 bitboard MC +
  `octogen_strategy.c` 1,883 + friends) plus ~8.6 KLOC of research bots that
  ship nowhere.
- Five consumer surfaces: three WASM modules (`bots.wasm` 159 KB /
  `rules.wasm` 36.7 KB / `guards.wasm` 6.5 KB — no libc, no imports,
  hand-rolled byte ABI), a static `libfoolish.a` xcframework for iOS/watchOS
  (32 `fio_*` exports, 23 actually called from Swift), and the native C
  server at `server/impls/native/` (5.5 KLOC) which compiles the kernel
  sources directly — no ABI at all.
- The minimum honest port scope is **5,540 LOC** (rules + wire codecs).
  With bridges and the shipped bots: ~20,600 LOC. ~10,600 LOC is droppable
  (research bots, CLI mains, dead `cnitro/src/game.h`, `json_out.c`'s
  TODO(delete) JSON surface).

## 2. Performance: measured, not argued

### 2.1 Where the CPU actually goes

- Callgrind profile of an octogen 2-player game
  (`server/impls/native/PROFILE_HOTPATH.md` §T3): **36.3%**
  `sim_solve_rec` (exact endgame alpha-beta, `cordite_sim.c:1397`), **19.9%**
  `sim_gen_moves` (`:1315`), 7.3% the 258-B per-node `memcpy` (`:1591`),
  6.6% `leafbook_key` (`leafbook.h:78`). At 6 players the exact solver share
  drops to ~14% and the bitboard rollout dominates.
- Per-move kernel compute on the serving path is **9.7 µs of a 5.1 ms
  end-to-end move** (`docs/PACKED_WIRE_CUTOVER.md`); `state_put` is 0.08% of
  the native server profile. The rules engine is not the bottleneck of
  anything user-visible.
- The C is heavily pre-optimized with banked measurements: bitboards (~4x),
  bitboard endgame solver (2.74x at 2p), `-flto` (~1.5x), TT
  2-way/packed-8-byte/4096-entry (1 MiB→32 KiB with *better* fidelity),
  LEAFBOOK perfect-hash endgame book (~15% e2e). Negative results are banked
  too (make/unmake, canonical TT keys, more MC worlds: all measured, all
  rejected) — a Rust port must not re-litigate these.

### 2.2 POC: four hot paths ported and measured (`rustpoc/`)

Method: workloads generated by the real engine (240 full games → 20,000
decision states, of which 1,774 are deck-empty 2-player endgames for the
solver; 2,000 real envelopes), C compiled from the actual `c/src` sources
with production flags (`clang -O3 -ffast-math -flto`, solver at the shipped
`-DCD_TT_BITS=12 -DCD_TT_2WAY -DCD_TT_PACK8`), Rust ports in safe Rust (std
only, zero `unsafe`, fat LTO, panic=abort). **Every Rust port reproduces the
C output checksum bit-for-bit — including the `double`-bearing rollout policy
against the `-ffast-math` build, and including the solver's exact node count:
all three implementations expand the identical 46,894,219-node search forest,
so TT probe/hit/eviction behavior is provably identical.** gcc runs calibrate
what "different compiler, same language" costs. Best-of-5 process invocations
(best-of-3 for the solver):

| bench | code under test | c-clang | c-gcc | rust (safe) | rust idiomatic |
|---|---|---|---|---|---|
| legal movegen, ns/call | `legal.c calculate_legal_moves` | 417 | **384** | 477 (+14%) | 433 (+4%) |
| MC playout, µs | `cordite_sim.c cd_sim_playout` + policy | **1.41** | 1.62 | 1.59 | — |
| **endgame solver**, Mnodes/s | `cordite_sim.c cd_sim_solve_d` (`sim_solve_rec` + movegen + TT — octogen's dominant cost) | **14.55** | 14.09 | 13.35 | — |
| envelope decode+encode, ns | `msg_wire.c msg_decode/encode` | 734 | 746 | **700** (−5%) | — |

Readings:

1. **The language deltas sit inside or near the compiler deltas.** gcc beats
   clang by 8% on movegen; clang beats gcc by 15% on playouts and 3% on the
   solver; Rust lands inside that band on three of four benches, and the
   direction flips per workload.
2. **The solver — octogen's actual hot path — is the honest worst case:
   +9% vs clang, +5.5% vs gcc, behind both.** Its inner loops are exactly
   the indexed-scratch code (depth-indexed move buffers, subset-mask
   scatters, TT buckets) where safe-Rust bounds checks cost and where
   `get_unchecked` would be needed for full parity. Context that bounds the
   damage: the solver is *node-budget-capped per decision* (octogen spends a
   fixed 400k/250k-node budget, ~30 ms/decision), so a 9% slower solver
   burns budget marginally faster rather than slowing the game loop 9%; and
   the per-node prefix-clone trick (`memcpy(child, s, offsetof(SimState,
   deck))`) ported to safe Rust cleanly as a struct split (`child.c = s.c`).
3. **Bounds checks are visible but partly recoverable without unsafe.** The
   faithful movegen port (+14%) pays for checked indexing in the recursive
   combination enumerators. The idiomatic variant — replacing
   `bool used[64]`/`bool seen[16]`/`bool table_values[16]` with `u64`/`u16`
   bitmasks, exactly the change the code-level review predicted — recovers
   to +4% *while emitting the byte-identical move sequence*. (C could adopt
   the same bitmasks; this is an algorithmic tweak Rust's idioms encourage,
   not a language speedup.)
4. **The hostile-bytes parser is where Rust is fastest** (−5%), with
   `from_le_bytes`/slice copies replacing byte loops — and that is also the
   surface where safety matters most.
5. **Bit-exact cross-language parity is achievable**, LCG, `f64` math, and
   the full alpha-beta/TT search tree included. This de-risks the single
   scariest part of a migration: the existing differential harnesses
   (`sim_difftest`, `apply_difftest`, `solver_difftest`, `bot_parity`, iOS
   goldens) can verify a Rust kernel move-for-move against the C oracle —
   including the solver, whose validation-ladder freeze looked like the
   hardest obstacle.
6. Struct sizes: Rust's field reordering shaved `SimState` 328→320 B and
   `MsgEnvelope` 616→608 B for free; everything else is parity. No memory
   win of consequence — the C already packs `Card` into 1 byte
   (`card.h:41-45`) and allocates nothing on any hot path.
7. A free corroboration: gcc's `-Warray-bounds` flags `cover_assign`'s write
   at offset 8 into `SolMove.cards[8]` while compiling the *unmodified*
   kernel for this bench — the same unguarded buffer §3.2 lists. (The Rust
   port's `[u8; 8]` would panic there instead of corrupting the neighbor
   field; our 16-card workload cannot reach it, and the checksums confirm
   neither side did.)

### 2.3 Why the compilers differ at all (callgrind, same source, same `-O3`)

The gcc↔clang spread is the yardstick this whole section leans on, so it is
worth showing it is real and understanding it. Measured with
`valgrind --tool=callgrind --branch-sim --cache-sim`:

**Legal movegen — gcc wins wall-clock by 8%, and simply emits less work:**

| | I refs (1 rep) |
|---|---|
| c-clang | 67,836,194 |
| c-gcc | **57,328,786 (−15.5%)** |

Identical source, identical flags, 15% fewer instructions executed. That is
inlining and unrolling policy on the recursive combination enumerators —
gcc's heuristics happen to fit that shape better. Here instruction count is
the whole story, and the 8% wall-clock win is a *damped* version of it.

**MC playout — clang wins wall-clock by 15% while executing the MOST
instructions.** This is the instructive one:

| | I refs | D refs | D1 miss | branches | mispredicts | mispred rate | µs/playout |
|---|---|---|---|---|---|---|---|
| c-clang | 62.37M | 35.66M | 208,015 | 27.01M | 501,228 | 1.9% | **1.41** |
| c-gcc | 60.81M | 34.25M | 205,511 | 27.40M | 497,298 | 1.8% | 1.62 |
| rust | **57.87M** | **19.14M** | 271,035 | **8.23M** | 579,226 | 7.0% | 1.59 |

Read the Rust column carefully: it executes **7% fewer instructions, 46%
fewer memory references, and 70% fewer branches** than clang — and is still
**13% slower**. The cost shows up in the two columns that stall a pipeline:
**16% more absolute branch mispredictions** (579K vs 501K, at ~15–20 cycles
each ≈ 1.2–1.6M wasted cycles) and **30% more L1-data misses** (271K vs
208K). Its 7.0% mispredict *rate* is partly an artifact — eliminating
easily-predicted loop-bound branches leaves a residue that is proportionally
harder to predict — but the absolute count rose too, and that is real time.

So the answer to "why would two compilers differ on the same code" is that
`-O3` is a pile of *heuristics* — inline/unroll thresholds, register
allocation and spill choices, block layout, when to vectorize — and none of
them is a solved problem. Two toolchains make different bets, and the bets
pay off differently depending on code shape: dense recursive enumeration
(gcc's win) versus a long chain of small branchy bitboard updates (clang's
win). The corollary that matters for the decision: **instruction count and
wall-clock are decoupled here, so "Rust generates worse code" is not what the
regressions show — Rust generates *denser* code that this hardware retires
less smoothly.** That is a scheduling/layout gap, the kind that moves with
compiler versions and target tuning, not a language-level ceiling.

**Conclusion: there is no decisive performance case in either direction. The
one measured Rust regression is single-digit, sits on the budget-capped
solver, and is recoverable with targeted `unsafe` if it ever mattered.**

## 3. The correctness ledger: what actually went wrong in C

This is the decision-relevant evidence. All from git history and in-tree docs.

### 3.0 Where this ledger lives (main vs branch)

Important framing, verified by comparing source across refs — not by commit
topology, since PR squash-merges give main different SHAs:

- **Kernel fixes reached `main`.** `origin/main:c/src/game.c` carries the
  bounded pickup append, `card.h` carries `card_mark_value`, and `MAX_LOGS`
  is 1024. So the kernel bugs below were real, are fixed, and the fixes are
  in the production kernel.
- **The server ledger is entirely off `main`.**
  `origin/main:server/impls/native/` holds 6 files and a **~600-line**
  `foolish_server.c` prototype — no `ws.c`, `conn.c`, `quic_wt.c`, or
  `persist.c`. The 3,612-line server, all six of its memory-safety bugs, and
  all six fixes live only on `claude/c-client-load-test-1j1rsj`. So "shipped"
  is the wrong word for those: they were introduced *and caught during
  development* of ~5.5 KLOC of fresh C, over roughly two weeks, by gates the
  author wrote. That is a **bug-density argument about writing new C**, which
  is precisely this project's situation — arguably stronger for a greenfield
  decision than a production-outage argument would be.
- **`6125fbe` (kernel globals → `_Thread_local`) is NOT on main**:
  `origin/main:c/src/game.h` still declares `extern int engine_last_reject;`.
  It is only needed once a threaded host drives the kernel, which today only
  the branch server does — but it means main's kernel is not thread-safe, and
  the fix must travel with the server whenever that merges.
- **Of the four live residuals in §3.2, exactly one is on `main`** —
  `state_get`'s missing length parameter, byte-identical in both refs. The
  other three (`ws.c:427`, `Content-Length`, QUIC token) are branch-only.
  That makes `state_get` the single highest-priority fix in this document,
  and it is a five-line C change that does not wait on any rewrite.

### 3.2 Live residuals (found during this examination, unfixed)

1. `server/impls/native/ws.c:427` — **the identical signed-shift UB fixed by
   `22efa79` survives in the second, hand-maintained copy of the same RFC
   6455 parser** (the `--tls` path). No fuzz gate ever reaches it and no gate
   builds it with UBSan. Two copies of one parser exist because C has no
   clean resumable-decoder abstraction; they have already diverged once.
2. `c/src/view.c:82` — **`state_get` takes no input length at all.** It
   clamps every count it writes (so the `Game` can't be corrupted) but reads
   as many bytes as the *content* implies — up to ~755 bytes past a
   truncated buffer. Reachable from a corrupt/attacker-writable DB blob via
   `deserialize_slot` (`foolish_server.c:453`). In Rust this signature is
   unwritable: a slice carries its length. (The honest cheap C fix is a
   length parameter — five lines.)
3. `foolish_server.c:1251` — `Content-Length` parsed by unbounded
   `cl = cl*10 + digit` into signed `int`; ten digits is UB. The fuzz corpus
   sends nine.
4. `quic_wt.c:111-129` — QUIC retry token with **no MAC** (forgeable,
   defeats address validation), plus O(n)-per-packet connection lookup and
   uncapped connection allocation.

Also on the unguarded-in-C list (from code review, not yet fired):
`game.c:711`/`:886` push into `table_battles[num_battles++]` with no
capacity check — the bound is *emergent* from a validation inequality, and at
the native build's `MAX_BATTLES=32` a legal post-pickup defender can exceed
it; `cordite_sim.c:1181` writes `ids[hn++]` into `int ids[16]` with `hn`
bounded only by a game-state popcount; `cover_assign` writes `m->cards[i]`
for up to 64 uncovered battles into an 8-byte array (`cordite_sim.c:1227`).
The SimState header itself documents an *observed* corruption of exactly this
class: "garbage atk ids ORed into hands as card bits >= 52 via pickup's
`1<<id`" (`cordite_sim.h:21-25`).

### 3.3 The machinery C requires to stay correct

- ~2,000 LOC of fuzz/ASan/stress shells + 4 build variants for the server;
  Helgrind/memcheck practice; a semantic anti-cheat fuzzer (`sem_fuzz.c`)
  with a negative control. **None of it runs in CI** — every C gate is
  manual. Rust subsumes roughly the sanitizer half (ASan/UBSan/Helgrind
  classes); the game-logic half (`sem_fuzz`'s invariants: card conservation,
  no foreign-card plays) transfers unchanged, because Rust proves none of it.
- 38 `_Static_assert`s, of which 32 police hand-rolled memory aliasing
  (overlay arenas, solver scratch), plus four Makefile comments warning that
  a header edit without a full rebuild "mixes layouts" — observed corruption
  from `-D`-driven struct dimensions across translation units.
  **Cap-set layout mixing is impossible under Cargo** — the strongest single
  build-system argument for Rust in the repo.
- Two lifetime contracts exist only as prose ("borrowed and NOT owned",
  `msg_wire.h:174`; "valid only for the duration of the sink call",
  `evwire.h:87`). In Rust these are `<'a>` annotations the compiler enforces
  — the POC wire port did exactly this.

## 4. Where C is genuinely better today (the honest cons)

1. **WASM size discipline.** `guards.wasm` is 6,505 B raw / 2,951 B gz with a
   **zero-byte data section**, zero imports, no allocator, memory pinned to
   one 64 KiB page so overflow is a *link error*. `rules.wasm` is 3 pages
   pinned. Matching this in Rust demands `no_std` + `panic_immediate_abort`
   + no `alloc` anywhere in the kernel + hand-rolled everything — achievable
   but it re-derives the entire `docs/WASM_L1_BUDGET.md` effort, and panic
   location strings/`core::fmt` are a real size regression risk on a 6.5 KB
   module. The manual overlay arenas (93 KiB saved by deliberately aliasing
   two never-live-together buffer families) become `unsafe` + a hand-written
   proof in Rust — parity at best.
2. **The solver's validation ladder.** Every behavior-affecting change to the
   MC/solver stack must re-pass thousands of paired games (V0–V6), and six
   seemingly-safe optimizations are documented as silently losing games.
   A port is a behavior-affecting change unless bit-exact. The POC proves
   bit-exactness is *achievable* for the rollout policy; the exact solver
   (TT warmth is outcome-affecting, `c/OCTOGEN.md`) is the hardest and
   should be ported last, behind `solver_difftest`.
3. **Hot-loop bounds checks.** The solver's inner 300 lines index scratch
   arrays with game-logic-proven bounds LLVM can't see; matching C exactly
   there means `get_unchecked` — `unsafe` in exactly the code the rewrite is
   supposed to protect. (The POC shows the tax is single-digit percent if
   simply accepted.)
4. **Toolchain simplicity.** make + clang, ~zero build deps (binaryen only).
   Kernel-in-Rust adds rustup to iOS/CI builds; a Rust *server* adds a
   250–450-crate supply chain that needs `cargo-audit`/`cargo-deny`. Supabase
   deploys are unaffected (they ship the committed `bots.wasm.gz`; CI never
   rebuilds wasm — which is its own problem, see §6).
5. **Per-file optimization mix.** `bots.wasm` compiles three MC files at
   `-O3` inside an `-Oz` module — measured worth ~15% p50 at −7 KB gz. Cargo
   has one `opt-level` per profile; matching this means crate splits along
   optimization lines.
6. **What Rust does *not* fix, on the record:** the stale-prebuilt-artifact
   class (`4edcb89`: the app shipped a stale kernel; Rust staticlibs have the
   identical failure mode), two-carriers-of-the-same-bytes drift (rules_wasm
   went stale for weeks), wasm LTO corrupting the indirect-function table
   (Rust `lto=true` needs the same empirical proof), capacity *sizing*, and
   logic/authorization bugs (`seat=-2`).

## 5. File-by-file: what a Rust port would concretely improve

Speed/memory (all modest; measured or code-derived):

| site | today | in Rust |
|---|---|---|
| `legal.c:239` `bool used[64] = {false}` per cover-enumeration leaf | ~4 KB of memset per movegen call at 6 uncovered battles; the frame this zeroes is the module's measured stack peak (`c/Makefile:508-517`) | `u64` bitmask in a register — **measured: recovers the faithful port's +14% to +4%** with byte-identical output |
| `legal.c:117,149` + `game.c:654` + `replay.c:743,1217` — five independent `bool[14..16]` "which ranks are on the table" tables, each with hand-written range guards | the guards exist because two live wasm traps came from this idiom | one `u16` rank bitset; guards vanish |
| `replay.c:768,788,815,863,876` `unseen_matching(...) > 0` | full 52-scan + insertion sort whose order is discarded, 5 sites per menu build | `(unseen & pred_mask) != 0` — one AND |
| `replay.c:391-412` `sorted_known`/`pref_sort` | O(n²) key recomputation inside insertion sort | decorate-sort; safe because the tree documents `(pref_key,id)` as a total order (wire format unaffected) |
| `replay_steps.c:214` `memset(&col,0,272 KiB)` per replay decode (live `/m/` path) | 80× over-zeroing | counter reset |
| `replay.c:234` `g_comb[52][52]` | 88% dead (only columns 0..5 read) — 19 KiB in a 3-page-pinned module | `[[u64;6];52]` |
| `SimState`/`MsgEnvelope` | 328 B / 616 B | 320 B / 608 B (free field reordering) |

Safety (the ones with a firing history or live exposure): `view.c:82`
`state_get` (no length — slice fixes by construction); `game.c:711,886`
unchecked battle pushes; `cordite_sim.c:275,326,1181,1227` unchecked
scratch writes (observed corruption class); `card.h` sentinel conventions →
`Option<Card>` with a niche (still 1 byte); `msg_wire.h`/`evwire.h` prose
lifetimes → `<'a>`; `Conn` tri-state → enum; the server's epoll pointer
graph → owned tasks/slab tokens.

Where Rust wins nothing: `deal_rng.c` (ChaCha, already optimal — and every
`+` becomes `wrapping_add`), `awire.c` (50 lines, provably bounded),
`state_put` (already vectorized, 0.08% of profile), the bignum limb loops,
`json_out.c` (hand-rolled *because* freestanding; `core::fmt` is bigger),
all algorithmic DoS caps (combinatorial-blowup guards must be rewritten
verbatim), and the frozen v5/v6 wire formats (only a second implementation
can check a format; the type system cannot).

## 6. Side findings that affect the decision (and should be fixed regardless)

- **The shipped wasm artifacts are stale**: `bots.wasm.gz` predates three
  kernel commits (including `9d17bea`, a change to `view.c state_put` — the
  shared wire serializer) and `rules_wasm.ts`/`guards_wasm.ts` are ~9 days
  staler. No CI job rebuilds wasm; the committed binary *is* production.
- `npm run test:mem` is red on the committed tree: `bots.wasm` declares 37
  pages, the gate asserts 36 (`e2e/mem/wasm_memory.test.ts:132`).
- `supabase/functions/_shared/wasm/` is a dead, orphaned duplicate kernel
  (different vintage!) reintroduced by an unrelated iMessage commit; nothing
  imports it. `cnitro/src/game.h` is a stale fork of `c/src/game.h` with
  `MAX_LOGS=512`. Both should be deleted — "two kernels in one tree" is the
  failure mode the Makefile itself warns about.
- The macOS/Xcode CI job is commented out: 165 Swift tests and the golden
  "keystone" never run in CI; `make tests`/`make difftests` run only inside
  the coverage job at reduced iterations; none of the server's fuzz/ASan
  gates run in CI at all. **Whatever language wins, the verification wiring
  is the first work item** — a rewrite verified by gates that don't run is
  not verified.

## 7. Recommendation

**Yes to Rust — phased, differential, and in this order:**

1. **Native server first** (5.5 KLOC; strongest case, and it is unmerged —
   so this is a decision about code with no deployment to protect). Six of
   its bugs were compile-time-preventable. On the "plumbing" share, measured
   by categorizing all 103 top-level functions in `foolish_server.c` by
   function span plus the whole of `ws.c`/`conn.c`/`quic_wt.c`/`persist.c`:
   **2,231 of 5,497 lines = 41%** (an earlier draft said 43%). The
   composition matters more than the headline, because the replaceability is
   uneven:
   - **~890 lines (16%) are textbook crate-replaceable**: RFC 6455 framing
     twice over (`ws.c` 464 + `wsasync_feed` 114 → `tokio-tungstenite`),
     HTTP/1.1 parse + response (110 → `httparse`), SHA-1/base64/base64url/
     HMAC-SHA256 + token codec (60 → `sha1`/`sha2`/`base64`/`hmac`), and the
     hand-rolled open-addressing table with its Knuth backward-shift delete
     (31 → `HashMap`). This is the part where a maintained, fuzzed crate is
     strictly better than what one author can hand-write, and it is where
     three of the four live residuals sit.
   - **~500 lines (9%) change shape rather than disappear**:
     `epoll/econn/acceptor` (349) + `conn.c` (151). `tokio`+`rustls` replace
     the *design* — and that is the real win, because it deletes the
     `--tls`-reverts-to-thread-per-connection compromise that forfeits the
     measured 71–73% memory saving and forced the duplicated parser — but
     connection-lifecycle logic still has to be written, just as owned tasks
     instead of a tombstone + deferred-free list.
   - **~835 lines (15%) are thinner wins than the headline suggests**:
     `quic_wt.c` (534) is glue over `libquiche` — which is *already Rust*
     with a C FFI, so `quinn` is a swap of one Rust QUIC stack for another
     (it does fix all three QUIC findings); `persist.c` (301) gets
     `rusqlite` for the driver, but the write-behind/batching policy is
     application logic that survives.

   Keep the kernel behind FFI initially — but give `state_get` a length
   parameter *now*, in C, regardless: it is the one live residual on `main`.
2. **Rules + wire core second** (5,540 LOC). Port `game.c`, `legal.c`,
   `view.c`, `awire.c`, `evwire.c`, `msg_wire.c`, `sha256.c`, `deal_rng.c`,
   then `replay.c` last within this phase (frozen format; its only oracle is
   itself — build the byte-corpus goldens before porting). Verify with the
   existing pattern: the tree already contains three engine-vs-engine
   difftests built for exactly this move, the iOS goldens transfer unchanged,
   and 47 of 84 e2e files just load a `.wasm` and don't care what produced
   it. The POC proves bit-exact parity is attainable.
3. **Bots/solver last, or never** (9.6 KLOC shipped). Weakest case: heavily
   optimized, behavior-frozen by the validation ladder, bounds-check-hostile
   inner loops — the solver POC measured the cost at +5.5–9% in fully safe
   Rust (recoverable with targeted `get_unchecked` if it matters) while also
   proving the port can be node-for-node bit-exact, which converts the
   validation-ladder freeze from a blocker into a checksum. Port only behind
   `sim_difftest`/`apply_difftest`/`solver_difftest` bit-exactness, and only
   after the core has soaked. An indefinite C tail here is a perfectly good
   end state; Cargo can link it via `cc`.
4. **Non-negotiables for the wasm targets**: `no_std`, no `alloc`,
   `panic_immediate_abort`, explicit export list, keep the memory pins and
   `wasm-opt` pass, and hold the Rust modules to the C numbers with
   `c/tools/wasm_anatomy` (it is language-agnostic). Treat `guards.wasm`
   (6.5 KB) as the acceptance test: if the Rust guards module can't get
   within ~2x of it, keep guards in C — it's 260 lines.
5. **Before any of it**: turn on the CI that exists (mem gate is currently
   red, difftests and fuzz gates don't run), delete the duplicate kernel
   carriers, and rebuild the stale wasm artifacts.

What tips it, given zero daily users: the migration risk that normally
dominates this decision is at its floor, the verification assets are already
built, and the bug ledger shows the residue that survives *careful* C here —
shift UB, uninitialized variants, iterator lifetimes, unenforced prose
invariants, divergent parser twins — is exactly the residue Rust removes at
compile time. The performance question, empirically, is a tie.
